# Phase 3.0 — Baseline: the logger and the five primitives

> **Principle:** *Schema is the contract — and what the LLM does is observable.*
> **Time:** ~38 minutes
> **Files touched:** 6 — `src/log.ts` (new), then `src/tools/search-monsters-by-category.ts`, `src/tools/get-monster-details.ts`, `src/tools/list-categories.ts`, `src/resources/monsters-categories.ts`, `src/prompts/analyze-monster.ts`

## Why

You're going to build a small MCP server. Three Tools, one Resource, one Prompt — and **a logger.**

Order matters. The logger comes first. Every iteration after 3.0 has an *Observe* step that asks you to watch what the LLM did. Without a server-side log, "watch" means "guess." With a log, "watch" means `tail -f logs/server.log` in a side terminal — four lines per primitive call.

The five primitives are the same shapes you've been previewed on. The handler bodies are empty — your job is to fill them in. Each one will:

1. Validate its input via Zod (already wired in the scaffold).
2. **Log the call.** `logCall(primitive, name, args)` on entry.
3. Do the work (a parameterised SQL query for most).
4. **Log the result.** `logResult(name, summary, durationMs)` on completion.
5. Return a `{ content: [...] }` envelope.

The lesson lands here, in your fingers, every time you write a Zod schema and a parameterised SQL query: **the schema is the contract.** The LLM cannot ask for invalid input. The query cannot be injected. The response shape is yours to choose. And from this iteration onwards, **every call the LLM makes shows up in your terminal.**

## Build the logger first

Create `src/log.ts`:

```typescript
// A small logger that grows across the module.
//
// Why log from 3.0? Every "Observe" beat below — every time we ask the LLM
// a question — we want to *see* which primitive fired, with what args,
// in what order. Without that, we're guessing. With it, we're watching.
//
// We write to TWO sinks:
//   1. logs/server.log — file you tail in a side terminal. This is the
//      workshop's observation surface, because Claude Code spawns its own
//      copy of the server (per .mcp.json) and you cannot see *its* stderr.
//      `tail -f logs/server.log` in a third terminal gives you the trace.
//   2. stderr (console.error) — visible when you run the server standalone
//      (smoke tests, manual debugging). stdout is the JSON-RPC channel —
//      NEVER log there or you break MCP.

import { appendFileSync, existsSync, mkdirSync } from "node:fs";

type Primitive = "tool" | "resource" | "prompt";

const LOG_DIR = "logs";
const LOG_FILE = `${LOG_DIR}/server.log`;

if (!existsSync(LOG_DIR)) mkdirSync(LOG_DIR, { recursive: true });

function emit(line: string): void {
  console.error(line);
  try {
    appendFileSync(LOG_FILE, line + "\n");
  } catch {
    // logging must never break the server
  }
}

export function logCall(primitive: Primitive, name: string, args: unknown): void {
  const ts = new Date().toISOString();
  emit(`[${ts}] ${primitive}=${name} args=${JSON.stringify(args)}`);
}

export function logResult(name: string, summary: string, durationMs: number): void {
  const ts = new Date().toISOString();
  emit(`[${ts}] result=${name} ${summary} ${durationMs}ms`);
}
```

Save. Your dev terminal hot-reloads — no errors expected because no one is calling it yet.

**Open a third terminal** and tail the log file so you can watch what the LLM does:

```bash
cd step-03
mkdir -p logs && touch logs/server.log     # so tail has something to follow
tail -f logs/server.log
```

This terminal stays open for the rest of Module 03. Every "Observe" beat below tells you what to expect in this stream.

## Fill in the handlers

### Tool 1 — `search_monsters_by_category` (longest; ~10 min)

Replace the TODO body in `src/tools/search-monsters-by-category.ts`. Add the import at the top:

```typescript
import { logCall, logResult } from "../log.ts";
```

Then the handler:

```typescript
async ({ category, limit }) => {
  const start = Date.now();
  logCall("tool", "search_monsters_by_category", { category, limit });

  const rows = await sql`
    SELECT m.name, m.monster_type, m.habitat, m.rarity
    FROM monsters m
    JOIN subcategories s ON s.subcategory_id = m.subcategory_id
    JOIN categories c ON c.category_id = s.category_id
    WHERE c.category_name = ${category}
    ORDER BY m.name
    LIMIT ${limit}
  `;

  if (rows.length === 0) {
    logResult("search_monsters_by_category", `found=0`, Date.now() - start);
    return {
      content: [{
        type: "text",
        text: `No monsters found in category "${category}".`,
      }],
    };
  }

  const lines = rows.map(
    (m) => `- **${m.name}** — ${m.monster_type} · ${m.habitat} · ${m.rarity}`,
  );

  logResult(
    "search_monsters_by_category",
    `found=${rows.length}`,
    Date.now() - start,
  );

  return {
    content: [{
      type: "text",
      text: `Found ${rows.length} monsters in category "${category}":\n\n${lines.join("\n")}`,
    }],
  };
},
```

**What just happened:**

- The Zod enum `z.enum(CATEGORIES)` (already in the scaffold) refuses any `category` value that isn't one of the six known categories. The handler can trust its input.
- The `sql\`...${category}...\`` tagged template **parameterises** `category` — no string concatenation, no SQL injection possible.
- `logCall` fires before the work; `logResult` fires after — both with timestamps and timing. **The `logs/server.log` tail shows the handler's lifecycle.**

### Tool 2 — `get_monster_details` (~5 min)

Same import. Handler:

```typescript
async ({ name }) => {
  const start = Date.now();
  logCall("tool", "get_monster_details", { name });

  const rows = await sql`
    SELECT
      m.name, m.monster_type, m.habitat, m.biome, m.rarity,
      m.height, m.weight, m.appearance,
      m.primary_power, m.secondary_power, m.special_ability,
      m.weakness, m.behavior_ecology, m.notable_specimens
    FROM monsters m
    WHERE LOWER(m.name) = LOWER(${name})
    LIMIT 1
  `;

  if (rows.length === 0) {
    logResult("get_monster_details", `not_found name="${name}"`, Date.now() - start);
    return {
      content: [{
        type: "text",
        text: `No monster found with name "${name}". Try \`search_monsters_by_category\` to browse.`,
      }],
    };
  }

  const m = rows[0]!;
  const text = [
    `# ${m.name}`,
    ``,
    `**Type:** ${m.monster_type} · **Habitat:** ${m.habitat} (${m.biome}) · **Rarity:** ${m.rarity}`,
    `**Size:** ${m.height} · ${m.weight}`,
    ``,
    `## Appearance`,
    m.appearance,
    ``,
    `## Powers`,
    `- **Primary:** ${m.primary_power}`,
    `- **Secondary:** ${m.secondary_power}`,
    `- **Special:** ${m.special_ability}`,
    ``,
    `## Weakness`,
    m.weakness,
    ``,
    `## Behaviour`,
    m.behavior_ecology,
    ``,
    `## Notable specimens`,
    m.notable_specimens,
  ].join("\n");

  logResult("get_monster_details", `found name="${m.name}"`, Date.now() - start);

  return {
    content: [{ type: "text", text }],
  };
},
```

**What just happened:** case-insensitive name lookup. Explicit "not found" response. Markdown-formatted output so Claude Code renders it nicely. **And:** the log line distinguishes a found-hit from a miss without you needing to grep through full response bodies.

### Tool 3 — `list_categories` (~3 min)

```typescript
async () => {
  const start = Date.now();
  logCall("tool", "list_categories", {});

  const rows = await sql`
    SELECT category_name, description
    FROM categories
    ORDER BY category_name
  `;

  const lines = rows.map(
    (c) => `- **${c.category_name}** — ${c.description}`,
  );

  logResult("list_categories", `count=${rows.length}`, Date.now() - start);

  return {
    content: [{
      type: "text",
      text: `Monster categories:\n\n${lines.join("\n")}`,
    }],
  };
},
```

**What just happened:** trivial bounded list. Notice we don't expose the `category_id` — it's an implementation detail. The LLM only ever sees names.

### Resource — `monsters://categories` (~5 min)

```typescript
async (uri) => {
  const start = Date.now();
  logCall("resource", "monsters://categories", { uri: uri.href });

  const rows = await sql`
    SELECT category_name, description
    FROM categories
    ORDER BY category_name
  `;

  logResult("monsters://categories", `count=${rows.length}`, Date.now() - start);

  return {
    contents: [{
      uri: uri.href,
      mimeType: "application/json",
      text: JSON.stringify(rows, null, 2),
    }],
  };
},
```

**What just happened:** same data as `list_categories`, exposed as a Resource. **Tools are for actions; Resources are for facts.** Different verbs, different cardinality. Both correct. And both visible in your `logs/server.log` tail.

We'll come back to this Resource in phases 3.1 and 3.3 — first to add a curated schema Resource alongside it, then to pre-cache it so reads don't hit the DB.

### Prompt — `analyze_monster` (~3 min)

```typescript
async ({ monster_name }) => {
  logCall("prompt", "analyze_monster", { monster_name });

  const text = `Analyse the monster called "${monster_name}".

Use the ragmonsters-server Tools. Cover these points:
1. Profile (category, type, habitat, rarity)
2. Powers (primary, secondary, special)
3. Weakness
4. One sentence on how you'd fight it`;

  return {
    messages: [{
      role: "user" as const,
      content: { type: "text" as const, text },
    }],
  };
},
```

**What just happened:** the simplest version of a Prompt — a single user message that asks the LLM to do something specific. **We'll upgrade this in phase 3.5** into a multi-step recipe naming specific Tools. For now, it works, and it's enough to show the Prompt mechanism end-to-end.

Note: a Prompt has no "result" to log — it just hands a message to the client. One `logCall` is enough.

## Common gotchas (phase 3.0)

| Symptom | Likely cause | Fix |
|---|---|---|
| `relation "monsters" does not exist` | Querying the wrong schema | The seed creates tables in `public` (no schema prefix). Don't write `ragmonsters.monsters` — just `monsters`. |
| `connection refused 127.0.0.1:5432` | `pglite/`'s `start:pg` not running | Restart `pglite/`'s `start:pg`; close any other Claude Code session holding the PGlite slot |
| Hot reload triggered but Claude Code shows stale Tool list | Client cached the list at handshake time | `/mcp` to force a re-list, or restart Claude Code |
| `logs/server.log` shows nothing when you ask the LLM something | Claude Code isn't actually calling your server | Check `/mcp` — `ragmonsters-server` must be listed; if not, `claude mcp reset-project-choices` and relaunch from `step-03/` |
| Dev terminal scrolls but `logs/server.log` is empty | You're watching the wrong process | The dev terminal runs *your* `bun --hot` copy; Claude Code spawned a *separate* copy from `.mcp.json`. Only the spawned copy actually serves MCP — its output goes to `logs/server.log`, not your dev terminal's stderr |
| Zod rejects a category that looks valid | Capitalisation mismatch — `"elemental"` vs. `"Elemental"` | Match the enum exactly: see `src/categories.ts` |
| Server breaks immediately on first request with cryptic JSON-RPC error | You wrote `console.log` instead of `console.error` somewhere | stdout is JSON-RPC; any non-JSON-RPC bytes on stdout corrupt the protocol. **All logging uses `console.error` or `appendFileSync`.** |
