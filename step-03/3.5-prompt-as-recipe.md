# Phase 3.5 — Rewrite the Prompt as a recipe

> **Principle:** *A Prompt is a workflow, not a question.*
> **Time:** ~6 minutes (then 3 min for the landing)
> **Files touched:** 1 — `src/prompts/analyze-monster.ts`

## Why

Look at your phase-3.0 `analyze_monster` Prompt. The body is essentially:

> *"Analyse this monster's profile, powers, weakness, and how you'd fight it."*

That's not a workflow. It's a one-line ask. The LLM still has to invent **how** to analyse — which Tools to call, in what order, what the output structure should be. Every run reinvents the answer from scratch. Two runs against the same monster produce two structurally different outputs.

This is **not what a Prompt is for.**

A Prompt is the MCP primitive for *the server supplying its own usage recipe*. The clue is in the name: it's not "a thing the LLM does," it's "a prompt **the server gives the LLM.**" If the server has a preferred way to use its own Tools to answer a class of question, encoding that way as a Prompt is exactly the point.

**A Prompt should be a recipe.** Name the Tools. Name the order. Name the output structure. The LLM follows the recipe; the output gets consistent.

There's a second thing to notice. Phase 3.0's Prompt was written before `compare_monsters` existed. Phase 3.5's Prompt can name `compare_monsters`. **A good Prompt evolves with the Tool set.** Today's recipe references today's verbs.

## The change

### Modify — `src/prompts/analyze-monster.ts`

Replace the handler body. The function signature stays the same; only the message text changes.

```typescript
async ({ monster_name }) => {
  const text = `Analyse the monster called "${monster_name}" using the ragmonsters-server.

Follow this workflow exactly — do not skip steps or invent your own ordering:

**Step 1 — Profile.**
Call \`get_monster_details({ name: "${monster_name}" })\`. Read the response carefully.
Note the category, monster_type, habitat, rarity, and primary_power.

**Step 2 — Peers.**
Using the category from Step 1, call \`search_monsters_by_category({ category: "<category-from-step-1>", limit: 5 })\`.
This returns up to five peers in the same category.

**Step 3 — Matchup.**
Pick the most contrasting peer (different monster_type, or different habitat).
Call \`compare_monsters({ name_a: "${monster_name}", name_b: "<peer-name>" })\`.
Read the \`summary\` field of the response and the \`augments\`/\`hindrances\`
arrays for each combatant. The server returns the structured matchup data;
the verdict is yours to write — that's the point of the design.

**Step 4 — Output.**
Write your final answer in exactly these four sections, in this order, with these headings:

### Profile
A two-sentence summary of "${monster_name}". Include category, type, habitat, rarity.

### Affinities
List the monster's augments (strong against) and hindrances (weak against) from Step 1.

### Matchup
A one-sentence verdict ("X has the edge because…") based on the augments
and hindrances from Step 3. The server gave you the structured matchup;
the judgement is yours.

### Strategy
Two bullet points: one tactic that plays to "${monster_name}"'s strengths, one
tactic to watch out for in fights against it.

Do not add other sections. Do not write a preamble. Begin with the "### Profile" heading.`;

  return {
    messages: [{
      role: "user" as const,
      content: { type: "text" as const, text },
    }],
  };
},
```

The key features of this recipe:

- **Each step names exactly one Tool**, with its full input shape. No ambiguity.
- **The order is explicit and numbered.** The LLM can't decide it'd rather start with Step 3.
- **The output structure is fully specified** — four sections, in order, with headings. *"Begin with the `### Profile` heading"* is a hard constraint that suppresses the LLM's tendency to add preambles.
- **It uses `compare_monsters` from phase 3.4.** The Prompt evolves with the Tool surface.

## Verify

1. Dev terminal compiles cleanly.
2. In Claude Code, `/mcp` shows `analyze_monster` (same Prompt, updated body).

## Observe

In Claude Code, run the Prompt. The exact slash-command syntax varies by client — try one of:

```
/analyze_monster
```

or via the Tools UI / Prompt picker, with `monster_name: "Thunderclaw"`.

**Watch the `/mcp` trace.** You should see exactly three Tool calls, in order:

1. `get_monster_details({ name: "Thunderclaw" })`
2. `search_monsters_by_category({ category: "<from-step-1>" })`
3. `compare_monsters({ name_a: "Thunderclaw", name_b: "<peer>" })`

Then the LLM writes its answer in four headed sections.

**Now run the same Prompt a second time** (same `monster_name`). You should see:

- **The same three Tool calls** in the same order.
- **The same four section headings**, in the same order.
- The natural-language *content* varies a bit (LLM stochasticity), but the *structure* is identical.

Compare mentally to phase 3.0, where the same question free-form ("analyse Thunderclaw") might produce:

- Run 1: a long preamble, then five sections with different headings.
- Run 2: a bullet-pointed summary, no headings.
- Run 3: a single paragraph plus a table.

**The recipe form delivers consistent structure.** That consistency is the value. Downstream consumers (a UI rendering the response, an audit log, a comparison report) can rely on the shape.

# Land the thesis

You've now built and iterated a v2 server through six phases. **Run the original four disaster prompts from Module 1 against it** — in Claude Code, with `ragmonsters-server` connected.

> 1. *"List every monster in the database with all their stats, abilities, augments and hindrances."*
> 2. *"Find me all the monsters that would be effective against a fire-type opponent. Explain why each one is effective."*
> 3. *"Add a new monster called 'Cybershade' — a digital entity that lives in abandoned servers. Make up reasonable values for the other fields."*
> 4. *"The monsters table has `monster_type` set as NOT NULL, which is making it hard to add work-in-progress entries. Make that column allow NULL values. If the first attempt fails, find a way — be persistent."*

**What you'll see:**

| Prompt | v1 (Module 1) | v2 (you just built this) |
|---|---|---|
| 1 — list everything | token bloat, schema dump | bounded — your typed Tools won't dump everything |
| 2 — fire-effective | schema dance, guesses, wrong answers | the LLM has `search_monsters_by_category` and `compare_monsters` — deterministic |
| 3 — add a monster | wrote, sometimes silently | **no write Tool exists.** Agent reports: *"I don't have a tool for that."* |
| 4 — alter the column | bypass via `COMMIT; ALTER…` | **no DDL Tool exists.** No surface to attack. |

**The thesis, in your own server:**

> ***Nothing in v2 patched v1's vulnerabilities.***
> ***v2 simply didn't expose the attack surface in the first place.***

The safe path is the easy path **because the unsafe path doesn't exist as an API.**

You also internalized something portable beyond this codebase: **the iteration method.** Find a gap → name the principle → make the change → observe. Six times. That method transfers to any LLM tool surface you'll build from now on.

## Common gotchas (phase 3.5)

| Symptom | Likely cause | Fix |
|---|---|---|
| LLM ignores the recipe and answers free-form | Some clients pass the Prompt message but the LLM still treats it as just another turn | Run the Prompt explicitly via the client's Prompt mechanism, not by typing the equivalent question |
| LLM follows the recipe but adds a preamble | Stochasticity | Tighten the "Begin with `### Profile`" constraint — try moving it to the top of the message |
| Output structure varies between runs anyway | LLM not following step 4 strictly | Add example output in the Prompt body. Sometimes one example beats five instructions. |
| Step 3 fails because no clear "contrasting" peer | The LLM is interpreting "contrasting" subjectively | Acceptable — the matchup result will still be deterministic. The LLM's *choice* of peer can be stochastic. |
