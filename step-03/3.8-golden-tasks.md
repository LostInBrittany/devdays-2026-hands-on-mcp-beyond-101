# Phase 3.8 — Test what the LLM actually does

> **Principle:** *Unit tests catch when your code is wrong. Golden tasks catch when the LLM uses your code wrong.*
> **Time:** ~12 minutes
> **Files touched:** 3 — `src/log.ts` (modify), `tests/golden-tasks.ts` (new), `scripts/run-golden-tasks.ts` (new)

## Why

LLMs are **non-deterministic callers.** You can ship a Tool that works perfectly — typed input, sanitized output, validated, authorised — and still have it called wrong by the LLM.

*Wrong* in this context means one of:

- Picked the wrong Tool. (Asked to "list elementals" — the LLM called `get_monster_details({name: "Elemental"})` instead of `search_monsters_by_category({category: "Elemental"})`.)
- Picked the right Tool with wrong args. (Used `search_monsters_by_category` with `category: "elemental"` lowercase — Zod rejects it.)
- Right call, wrong order. (Called `compare_monsters` before fetching details — possible after 3.5's Prompt landed, but maybe regresses if a future Prompt drift removes that order.)

You don't catch any of those with a unit test on the handler. The handler isn't wrong; the *LLM's choice of which handler to call* is wrong. **You need a different kind of test for that.**

The pattern is **golden tasks** (Devoxx UK 4f, Anthropic's "agent evals"):

> A representative prompt with an expected *tool sequence*.
> Not: *"does the tool work?"*
> But: *"does the LLM pick the right tool, with the right arguments, in the right order?"*

For the workshop, we build a **manual** harness — instructor or participant runs each prompt by hand in Claude Code, the harness validates the captured logs against the expected sequence. The shape of the test is the same as a production runner; just the driver differs. We'll cover the production version at the end.

**Principle:** *Test what the LLM actually does.*

## The change

### Modify — `src/log.ts`

Add the JSONL writer. Existing `console.error` lines stay; we just tee to a file as well.

```typescript
import { appendFileSync, existsSync, mkdirSync } from "node:fs";

type Primitive = "tool" | "resource" | "prompt";

const GOLDEN_LOG = process.env.GOLDEN_LOG === "1";
const GOLDEN_LOG_FILE = "logs/golden.jsonl";

if (GOLDEN_LOG && !existsSync("logs")) {
  mkdirSync("logs", { recursive: true });
}

function maybeAppendGoldenLog(entry: object): void {
  if (!GOLDEN_LOG) return;
  try {
    appendFileSync(GOLDEN_LOG_FILE, JSON.stringify(entry) + "\n");
  } catch {
    // logging must never break the server
  }
}

export function logCall(primitive: Primitive, name: string, args: unknown): void {
  const ts = new Date().toISOString();
  console.error(`[${ts}] ${primitive}=${name} args=${JSON.stringify(args)}`);
  maybeAppendGoldenLog({ kind: "call", ts, primitive, name, args });
}

export function logResult(name: string, summary: string, durationMs: number): void {
  const ts = new Date().toISOString();
  console.error(`[${ts}] result=${name} ${summary} ${durationMs}ms`);
  maybeAppendGoldenLog({ kind: "result", ts, name, summary, durationMs });
}
```

When `GOLDEN_LOG` is unset (the default), behaviour is identical to 3.7. When `GOLDEN_LOG=1`, every `logCall`/`logResult` *also* appends one JSON line to `logs/golden.jsonl`. **One knob, opt-in, no impact on day-to-day dev work.**

### New file — `tests/golden-tasks.ts`

```typescript
// Golden tasks for ragmonsters-server.
//
// Each task names a prompt and the tool sequence we expect the LLM to use.
// `args_match` is a regex over the JSON-stringified args — keep it loose
// enough that minor LLM variation passes, tight enough that wrong-tool or
// wrong-args fails.

export type ExpectedCall = {
  primitive: "tool" | "resource" | "prompt";
  name: string;
  args_match?: RegExp;
};

export type GoldenTask = {
  name: string;
  prompt: string;
  expected_calls: ExpectedCall[];
};

export const TASKS: GoldenTask[] = [
  {
    name: "list elementals",
    prompt: "List Elemental monsters.",
    expected_calls: [
      {
        primitive: "tool",
        name: "search_monsters_by_category",
        args_match: /"category"\s*:\s*"Elemental"/,
      },
    ],
  },
  {
    name: "compare two monsters",
    prompt: "Who would win — Thunderclaw or Aquafrost?",
    expected_calls: [
      {
        primitive: "tool",
        name: "compare_monsters",
        args_match: /Thunderclaw.*Aquafrost|Aquafrost.*Thunderclaw/,
      },
    ],
  },
  {
    name: "fetch one monster's details",
    prompt: "Tell me everything about Cinderwing.",
    expected_calls: [
      {
        primitive: "tool",
        name: "get_monster_details",
        args_match: /"name"\s*:\s*"Cinderwing"/i,
      },
    ],
  },
];
```

Three tasks is enough for the workshop. **Add three more of your own as stretch.** At least one should test something you suspect might regress — e.g., the `analyze_monster` Prompt's three-tool recipe from 3.5.

### New file — `scripts/run-golden-tasks.ts`

```typescript
#!/usr/bin/env bun
//
// Manual golden-task harness for the workshop.
//
// Workflow:
//   1. For each task, the harness clears logs/golden.jsonl.
//   2. It prints the prompt to copy into Claude Code.
//   3. You run that prompt; when Claude Code finishes, you press Enter.
//   4. The harness reads logs/golden.jsonl and validates the captured
//      call sequence against the expected one.
//
// The server must be running with `GOLDEN_LOG=1` so it writes to the
// JSONL file the harness reads.

import {
  existsSync, mkdirSync, readFileSync, writeFileSync,
} from "node:fs";
import { createInterface } from "node:readline/promises";

import { TASKS, type ExpectedCall, type GoldenTask } from "../tests/golden-tasks.ts";

const LOG_FILE = "logs/golden.jsonl";

type LogEntry =
  | { kind: "call"; primitive: "tool" | "resource" | "prompt"; name: string; args: unknown }
  | { kind: "result"; name: string; summary: string; durationMs: number };

function readCalls(): LogEntry[] {
  if (!existsSync(LOG_FILE)) return [];
  const text = readFileSync(LOG_FILE, "utf-8");
  return text.split("\n").filter(Boolean).map((line) => JSON.parse(line));
}

function findMatchingCall(
  expected: ExpectedCall,
  captured: LogEntry[],
  startAt: number,
): number {
  for (let i = startAt; i < captured.length; i++) {
    const entry = captured[i]!;
    if (entry.kind !== "call") continue;
    if (entry.primitive !== expected.primitive) continue;
    if (entry.name !== expected.name) continue;
    if (expected.args_match) {
      const argsStr = JSON.stringify(entry.args);
      if (!expected.args_match.test(argsStr)) continue;
    }
    return i;
  }
  return -1;
}

function assertSequence(
  captured: LogEntry[],
  expected: ExpectedCall[],
): { pass: true } | { pass: false; reason: string } {
  let cursor = 0;
  for (const exp of expected) {
    const idx = findMatchingCall(exp, captured, cursor);
    if (idx < 0) {
      // Filter the "auth" pseudo-calls out of the captured trace before
      // reporting so the output is human-readable.
      const visible = captured
        .filter((e): e is Extract<LogEntry, { kind: "call" }> =>
          e.kind === "call" && e.name !== "auth" && e.name !== "sanitize",
        )
        .map((e) => `${e.primitive}=${e.name}`);
      return {
        pass: false,
        reason:
          `Expected ${exp.primitive}=${exp.name}` +
          (exp.args_match ? ` matching ${exp.args_match}` : "") +
          `. Captured (filtered): [${visible.join(", ")}]`,
      };
    }
    cursor = idx + 1;
  }
  return { pass: true };
}

async function runTask(task: GoldenTask, rl: ReturnType<typeof createInterface>): Promise<boolean> {
  console.log(`\n=== ${task.name} ===`);
  console.log(`Open Claude Code and ask:\n  "${task.prompt}"\n`);
  await rl.question("Press Enter once Claude Code has finished... ");

  const captured = readCalls();
  const result = assertSequence(captured, task.expected_calls);

  if (result.pass) {
    console.log(`  ✓ pass`);
    return true;
  } else {
    console.log(`  ✗ fail: ${result.reason}`);
    return false;
  }
}

async function main() {
  if (!existsSync("logs")) {
    mkdirSync("logs", { recursive: true });
  }

  const rl = createInterface({ input: process.stdin, output: process.stdout });
  console.log(`Golden tasks — ${TASKS.length} tasks. Make sure your server runs with GOLDEN_LOG=1.\n`);

  let pass = 0, fail = 0;
  for (const task of TASKS) {
    writeFileSync(LOG_FILE, "");        // clear before each task
    const ok = await runTask(task, rl);
    if (ok) pass++; else fail++;
  }

  rl.close();
  console.log(`\n────────────────────────────`);
  console.log(`${pass}/${TASKS.length} passed.`);
  process.exit(fail === 0 ? 0 : 1);
}

await main();
```

The LLM doesn't pick `compare_monsters` any more — the description no longer matches the user intent. It might call `get_monster_details` twice and reason instead, or it might give up and ask the user. **The harness reports the failure:**

```
=== compare two monsters ===
Open Claude Code and ask:
  "Who would win — Thunderclaw or Aquafrost?"

Press Enter once Claude Code has finished...
  ✗ fail: Expected tool=compare_monsters matching /Thunderclaw.*Aquafrost.../. Captured (filtered): [tool=get_monster_details, tool=get_monster_details]
```

**No code changed.** The Tool's behaviour is identical. **Only the description changed**, and the LLM's behaviour changed with it. Unit tests would never catch this. Golden tasks do.

## Real-life note — what the manual harness leaves out

What you built is workshop-scale: manual driver, JSONL log, regex args matching. A production golden-task suite needs more:

1. **A real LLM driver.** Replace the human-running-Claude-Code step with the Anthropic SDK directly: `client.messages.create({ tools: [...], temperature: 0 })`. Tool calls come back in `message.content` as `tool_use` blocks — no log scraping needed.
2. **Server lifecycle.** Spawn the MCP server fresh per test (or use the MCP TypeScript SDK's `Client` to connect over stdin/stdout) so tests don't share state.
3. **CI integration + cost/latency budget.** Each test is a real LLM call. Budget per PR. Cache fixtures (recorded LLM responses) so most CI runs don't hit the API; refresh on schema/Tool changes.
4. **Determinism strategy.** Temperature 0, pinned model version, document the assertion tolerance for natural-language fields. Golden tasks aren't snapshot tests — they assert on *tool sequences*, which are far more stable than text outputs, but you still think about model-version drift.

The shape stays the same: prompt → captured tool calls → assert against expected. The runner gets industrial; the principle doesn't.

## Common gotchas (phase 3.8)

| Symptom | Likely cause | Fix |
|---|---|---|
| `logs/golden.jsonl` is empty after a prompt | Server isn't running with `GOLDEN_LOG=1` | Restart server: `GOLDEN_LOG=1 bun --hot run src/server.ts` |
| Harness says "Expected tool=X" but the right tool name appears in the captured trace | `args_match` regex is too strict (or wrong) | Loosen the regex. Test it against the actual JSON in `logs/golden.jsonl` |
| "compare two monsters" task always fails with auth_denied | Server isn't running with `MCP_PRINCIPAL=developer` | Restart: `GOLDEN_LOG=1 MCP_PRINCIPAL=developer bun --hot run src/server.ts` |
| Harness prints prompt but Enter doesn't continue | You're in the wrong terminal — the harness owns stdin in *its* terminal | Press Enter in the harness's terminal, not the server's |
| Log file has lines from previous prompts | The harness clears the log before each task, but if you re-ran the prompt in between, those calls land in the next task's window | Re-run the harness from scratch; don't poke Claude Code between tasks |
