# Phase 3.1 — Curated schema Resource

> **Principle:** *Expose intent, not structure.*
> **Time:** ~10 minutes (split into two beats)
> **Files touched:** 2 — `src/resources/schema.ts` (new), `src/server.ts` (modify, twice)

## Why

In Module 1, the v1 server's auto-injected schema was the **first** thing that broke. Every public table's columns were published as a Resource the client auto-loaded on connection. Nine tables, hundreds of tokens of raw metadata before any actual question was asked.

The wrong takeaway from that disaster is *"v2 should expose no schema."* That's overcorrecting. A server that hides its data model from its caller is just a different kind of unusable.

The right takeaway is **v2 should expose schema deliberately.** A *hand-written, intent-shaped* description of what's in the database — what concepts the data represents, what relationships matter, what the caller should reach for first. **Not** a dump of `information_schema.columns`.

This is the same trade-off REST APIs faced in the early 2010s. The auto-generated WSDL-style schema dumps gave way to hand-written OpenAPI summaries because *humans (and now LLMs) reason better about intent than about structure.*

We're going to add a `monsters://schema` Resource. The Resource handler returns a Markdown-ish text blob that describes the database **as a domain**, not as a relational layout.

But — and this is the surprise that makes 3.1 a two-beat iteration — **publishing a Resource isn't the same as the LLM reading it.** Beat 2 confronts that.

## Files touched

```
src/resources/schema.ts    ← new file (~50 lines)
src/server.ts              ← Beat 1: add import + register call
                              Beat 2: add `instructions` to McpServer
```

## Steps

**Beat 1 — build the Resource (4 min)**

1. Create the new file `src/resources/schema.ts` (full content below).
2. Modify `src/server.ts` to register the new Resource (one import, one register call).
3. Save both files — your `bun --hot` dev terminal hot-reloads.
4. In Claude Code, `/mcp` — verify the new Resource shows up under `ragmonsters-server`.
5. Send the OBSERVE prompt from **Beat 1 — Observe** below. Watch what happens. (You may be surprised.)

**Beat 2 — nudge the client to actually read it (4 min)**

6. Modify `src/server.ts` again to add an `instructions` field to the `McpServer` constructor.
7. **Restart your Claude Code session.** Server `instructions` ride the initialize handshake — they're sent once at connection time, so hot-reload alone won't deliver them to a client that's already connected. Quit Claude Code, re-enter, re-attach to the server.
8. Send the OBSERVE prompt from **Beat 2 — Observe** below. Compare what you see to Beat 1.

## Beat 1 — The change

### New file — `src/resources/schema.ts`

```typescript
// Resource: monsters://schema
//
// A hand-written, intent-shaped description of the RAGmonsters database.
// Notice what this is NOT: it's not a dump of column names, types, indexes,
// or constraints. v1 did that and it bit us — 9 tables of raw schema burning
// the LLM's context budget before a single question.
//
// What this IS: a domain description. "Here are 30 monsters. Here's how
// they're categorised. Here's where their stats live. Here's what each
// Tool will help you with." The LLM gets the model in English, not in DDL.

import type { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";

const SCHEMA_DESCRIPTION = `# RAGmonsters database overview

A catalogue of 30 fictional monsters used as a recurring teaching example.
The data lives across nine normalised tables, but you should reason about
it as a domain, not a relational schema.

## The domain in one paragraph

Every monster has a **name** (e.g. "Thunderclaw", "Aquafrost"), belongs to
a **category** (one of six: Elemental, Construct/Artificial, Anomaly/Phenomenon,
Nature/Organic, Celestial/Cosmic, Spirit/Ethereal) via a **subcategory**, and
lives in a **habitat** within a **biome**. It has narrative attributes
(appearance, weakness, behaviour, notable specimens) and a QuestWorlds stats
subtree (keywords, abilities, flaws). It also has typed **augments**
(creatures it's strong against) and **hindrances** (creatures it's weak
against) for matchup calculations.

## What the Tools give you

- \`search_monsters_by_category(category, limit?)\` — find monsters in one
  of the six bounded categories. Start here when the user asks "show me
  X-type monsters."
- \`get_monster_details(name)\` — full profile for one monster. Use after a
  search to drill down, or directly when the user names a monster.
- \`list_categories()\` — the six categories with descriptions. Use when
  the user asks "what kinds of monsters exist?" (Also available as the
  \`monsters://categories\` Resource — cacheable.)

## What we deliberately do NOT expose

- No raw SQL. The LLM cannot write queries against the underlying tables.
- No schema modification (no DDL). The LLM cannot add columns, drop tables,
  or change types. This is intentional — v2 is read-only.
- No bulk operations. The LLM cannot fetch all monsters at once.

If you find yourself wanting one of those, you've left the v2 design surface.
That's a signal to step back and decide whether the use case deserves a new
Tool — or whether the LLM should compose existing Tools instead.
`;

export function registerSchemaResource(server: McpServer) {
  server.registerResource(
    "monsters-schema",
    "monsters://schema",
    {
      description:
        "Hand-written domain overview of the RAGmonsters dataset. Read this first to understand what Tools to reach for.",
      mimeType: "text/markdown",
    },
    async (uri) => ({
      contents: [{
        uri: uri.href,
        mimeType: "text/markdown",
        text: SCHEMA_DESCRIPTION,
      }],
    }),
  );
}
```

### Modify — `src/server.ts` (Beat 1)

Add one import line near the top with the other Resource imports:

```typescript
import { registerSchemaResource } from "./resources/schema.ts";
```

Then add one register call alongside the existing Resource registration. The relevant block becomes:

```typescript
// Resources — the cacheable facts.
registerMonstersCategoriesResource(server);
registerSchemaResource(server);                  // ← NEW
```

## Beat 1 — Observe

In Claude Code:

> *"What's in this database? Don't run any queries yet — just tell me what kind of data is here."*

**Now — what actually happens, depending on your client?**

You'll likely see **one of two things**:

- **(a)** Claude Code answers in vague terms: *"This looks like a Postgres database with monsters. I could run `list_categories` to find out more — want me to?"* It never reads `monsters://schema`. The Resource we just built is invisible to the model.
- **(b)** Claude Code calls `ReadMcpResourceTool` on `monsters://schema` and answers in rich domain terms.

**If you got (a), do not panic — that is the point of Beat 2.**

### Why this happens — the application-controlled tier

In the MCP spec, the three primitives have three different *control tiers*:

| Primitive | Control tier | Who decides when it's used |
|---|---|---|
| **Tool** | model-controlled | the LLM picks a Tool based on tool descriptions in its context |
| **Resource** | **application-controlled** | the **host application** decides whether and how to surface Resources |
| **Prompt** | user-controlled | the user explicitly invokes a Prompt (e.g. via a slash command) |

The host application — Claude Code, Claude Desktop, ChatGPT connectors, Cursor, etc. — implements its own policy for Resources. Some hosts auto-inject them into the LLM's context on connection. Some surface them as `@`-mentions the user can pull in by hand. **Claude Code gates Resources behind two meta-tools — `ListMcpResourcesTool` and `ReadMcpResourceTool` — and the LLM only sees a Resource if it decides on its own to call one of those tools.** Whether that decision fires depends on the tool descriptions, the user's prompt, and the model's mood.

So: *publishing a Resource is not the same as the LLM consuming it.* The server has done its job. The host has done its job. The gap between them is real, and it's not a bug in either side — it's the design tier expressing itself.

**This is exactly the lesson the workshop's spine promises.** *MCP servers are APIs.* And like every API: how the client consumes you is not under your control. You can ship a beautiful OpenAPI document and watch a client ignore it. The only thing you control is the contract you publish.

### What the server *can* do about it

The MCP spec gives a server exactly one channel to nudge the host: the `instructions` field on the initialize handshake. The server sends a string at connection time; clients that respect it inject that string into the LLM's context as session-level guidance. (This is the same mechanism the `claude-in-chrome` extension uses to tell Claude *"load tools via `ToolSearch` first."*)

We're going to use `instructions` to point the LLM at our schema Resource. That's Beat 2.

## Beat 2 — The change

### Modify — `src/server.ts` (Beat 2)

The `McpServer` constructor takes a second argument: a server-options object. Put `instructions` there:

```typescript
const server = new McpServer(
  {
    name: "ragmonsters-server",
    version: "0.1.0",
  },
  {
    instructions: [
      "This server exposes a small catalogue of fictional monsters (the RAGmonsters dataset).",
      "",
      "Before using any Tool for the first time in a conversation, read the `monsters://schema` Resource. It describes the domain (six monster categories, what each Tool does, what is deliberately not exposed) and will save you from guessing category names or Tool semantics.",
      "",
      "Quick map:",
      "- `monsters://schema` — hand-written domain overview. Read first.",
      "- `monsters://categories` — the six valid category names with descriptions.",
      "- Tools: `search_monsters_by_category`, `get_monster_details`, `list_categories`.",
    ].join("\n"),
  },
);
```

### Why phrase it this way

- **Tell the LLM what to do, not what to know.** "Read `monsters://schema` first" is an action it can take. "There is a schema Resource available" is a fact it can forget.
- **Justify the action.** *"…will save you from guessing category names or Tool semantics"* — give the model a reason. Reasons stick where commands don't.
- **Keep it short.** This string ships on every initialize. Bloating it costs tokens on every session.
- **Don't duplicate the Resource's body.** The point is to make the LLM *fetch* the Resource, not to replace it. Putting the full domain overview here would be missing the point — we'd be back to "v1 auto-injects everything."

## Beat 2 — Verify

1. Dev terminal recompiled cleanly.
2. **Restart your Claude Code session.** (Quit and re-enter.) `instructions` is sent on the initialize handshake — an already-connected client won't see the new value.
3. In `logs/server.log`, the next initialize line should reflect the new handshake.

## Beat 2 — Observe

Same prompt as Beat 1:

> *"What's in this database? Don't run any queries yet — just tell me what kind of data is here."*

**Now watch the difference:**

- The LLM calls `ReadMcpResourceTool` on `monsters://schema` *before* answering. Visible in the trace.
- `logs/server.log` shows `resource=monsters://schema` being read.
- The answer is in domain terms: *"30 monsters across six categories with narrative profiles and QuestWorlds stats…"* — the words from your hand-written description.

**This is the contrast that lands the lesson.** Same server, same Resource, same prompt. The only change is one string in the handshake. Without it, the carefully-curated Resource was invisible. With it, the LLM reaches for it without being asked.

## What this iteration actually taught

Two things, stacked:

1. **Expose intent, not structure.** A hand-written domain overview beats a column dump. (The Beat 1 lesson.)
2. **Resources are application-controlled — design around that.** Publishing a Resource is necessary but not sufficient. The server's only steering wheel for resource adoption is `instructions`. Use it. (The Beat 2 lesson — and the deeper one, because it generalises: every MCP design choice has to account for how the host will surface it.)

Compare mentally to Module 1: when Claude Code first connected to the v1 server, it auto-loaded nine tables' worth of column metadata. Now it reads one human-written paragraph and *knows what to do next.* And the *reason* it reads that paragraph is a 200-token nudge in the handshake — not the LLM's politeness.

The token cost of `instructions` + the schema Resource is roughly the same as one of v1's auto-injected table schemas. But the *information density* is much higher — it tells the LLM **how to use the API**, not just what columns exist.

**That's the lesson:** the same token budget, spent on intent instead of structure (and on a channel the host respects), is dramatically more useful.

## Common gotchas (phase 3.1)

| Symptom | Likely cause | Fix |
|---|---|---|
| `monsters://schema` doesn't show in `/mcp` | Forgot the register call in `server.ts` | Add the line, save, re-check |
| `instructions` change has no effect | Forgot to restart the Claude Code session — `instructions` only ships on initialize | Quit and re-enter Claude Code |
| LLM still ignores the schema after restart | Some hosts ignore `instructions` (treat it as advisory). Spec says "clients SHOULD" not "MUST" | Acknowledge the limit; fall back to mentioning `monsters://schema` in tool descriptions (preview of a pattern we lean on more in 3.2) |
| TypeScript error about the second McpServer arg | SDK version mismatch | `bun install` to confirm `@modelcontextprotocol/sdk` is `^1.0.0` (≥ 1.29.0) |
