# Phase 3.4 — `compare_monsters` as a 4th Tool

> **Principle:** *Add a verb when the use case demands it.*
> **Time:** ~10 minutes
> **Files touched:** 2 — `src/tools/compare-monsters.ts` (new), `src/server.ts` (modify)

## Why

By phase 3.3, you have a working server with three Tools, two Resources, one Prompt, and the LLM following hypermedia hints. **Now stop and watch the LLM use it.**

Ask Claude Code, with your phase-3.3 server:

> *"Who would win in a fight — Thunderclaw or Aquafrost?"*

Watch the `/mcp` trace. The LLM:

1. Calls `get_monster_details({ name: "Thunderclaw" })` — gets the profile.
2. Calls `get_monster_details({ name: "Aquafrost" })` — gets the profile.
3. **Reasons about the matchup in its head** — compares categories, looks at primary/secondary powers, applies fictional type matchups, picks a winner.

It works. But you should notice two things:

- The LLM did **the same two-step pattern** twice. If you ask another matchup question, it'll do it again.
- Two tool calls + reasoning = two round trips' worth of context cost, and the LLM is reconstructing the comparison from two separate Tool outputs.

**This is the signal that a new Tool is justified.** When the LLM keeps composing the same two-or-three calls to do *one logical thing*, that thing wants to be a Tool of its own.

Compare to the wrong reason to add a Tool: *"we have a SQL query we could expose."* That's a *capability-driven* expansion — it grows the API surface without a use case driving it. Capability-driven expansion is how v1 got 9 tables exposed as Resources nobody asked for.

**Use-case-driven expansion is the right pattern.** The LLM was already trying to compare monsters; we noticed; we add the Tool. Adding it *now* (phase 3.4 instead of 3.0) is deliberate — we couldn't have predicted the need without watching the LLM struggle in 3.0–3.3.

### Sub-principle: data join server-side, judgement caller-side

There's a temptation when adding `compare_monsters` to also have the server *decide who wins.* "Compute it deterministically," the argument goes — "the LLM's verdicts drift across runs."

**We're not going to do that, and naming the reason is part of the lesson.**

The data the server has access to looks like this:

- Thunderclaw's augments: `target_name = "Water creatures", modifier = +5`
- Aquafrost's hindrances: `target_name = "Electric creatures", modifier = -5`
- Aquafrost's `category_name` (a column) is `"Elemental"`. Its `monster_type` is something like `"Water/Ice hybrid"`.

To compute a verdict, the server would need to ask: *"Does `'Water creatures'` describe Aquafrost?"* The columns the server has are `"Elemental"` and `"Water/Ice hybrid"` — neither contains the substring `"water creatures"`. Any naive match returns nothing. The verdict comes out as `"roughly even"` even though Thunderclaw clearly wins.

This is **fuzzy semantic matching across vocabularies**: free-text augment targets (`"Water creatures"`) vs. structured category/type columns (`"Elemental"`, `"Water/Ice"`). LLMs are excellent at this. A server doing string-includes is not.

The lesson generalises beyond this Tool:

- **Compute server-side** when the work is a deterministic join across tables, a numerical aggregation, a filtered query — things SQL was designed for.
- **Leave to the LLM** when the work is fuzzy interpretation, ranking on incompatible vocabularies, narrative synthesis, weighing of intangibles.
- **A deterministically-wrong verdict is worse than no verdict at all** — it actively misleads downstream callers who might trust it. (When we shipped this Tool with a broken verdict in an earlier draft, the LLM *correctly overrode it*. That's the model saving the server from itself. Better to not put the server in that position.)

So `compare_monsters` ships the structured comparison data — both monsters' categories, types, primary powers, full augments and hindrances tables — and stops there. The `summary` field tells the LLM how to read the data. No `verdict` field. The Tool's job is to consolidate the two-call pattern into one round trip and present the comparison clearly; the verdict stays with the caller.

This is one of the most important production MCP design principles. Know which side of the wire each kind of work belongs on.

## The change

### New file — `src/tools/compare-monsters.ts`

```typescript
// Tool: compare_monsters
//
// Added in 3.4 after observing the LLM repeatedly compose two get_monster_details
// calls + post-hoc reasoning to answer "who wins, X vs. Y?" questions.
//
// Design choice — what this Tool does (and what it deliberately doesn't):
//   - DOES: a single-round-trip join across monsters + augments + hindrances for
//     both combatants. The expensive, deterministic, structural work is server-side.
//   - DOES NOT: compute an overall "winner" verdict. Type-matchup reasoning means
//     reading "Water creatures" (free text) against "Aquafrost" (a name) and
//     "Elemental" (a category). That's fuzzy semantic matching across vocabularies
//     — exactly what LLMs do well and what a substring-checking server does badly.
//
// Lesson: compute joins server-side, leave judgement to the caller.
// A deterministically-wrong verdict is worse than no verdict at all.

import { z } from "zod";
import type { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";

import { sql } from "../db.ts";

type MonsterRow = {
  monster_id: number;
  name: string;
  monster_type: string;
  habitat: string;
  rarity: string;
  primary_power: string;
  category_name: string;
};

type Affinity = { target_name: string; modifier: number };

export function registerCompareMonsters(server: McpServer) {
  server.registerTool(
    "compare_monsters",
    {
      description:
        "Side-by-side comparison of two monsters in a single round-trip: categories, types, rarities, primary powers, and full augments/hindrances tables for both. Returns the structured data — assessment of who wins is left to the caller, since fuzzy type-matchup reasoning is something LLMs do well and a server doing substring matching does badly.",
      inputSchema: {
        name_a: z.string().min(1).describe("Name of the first monster (case-insensitive)."),
        name_b: z.string().min(1).describe("Name of the second monster (case-insensitive)."),
      },
    },
    async ({ name_a, name_b }) => {
      const rows = await sql<MonsterRow[]>`
        SELECT m.monster_id, m.name, m.monster_type, m.habitat, m.rarity,
               m.primary_power, c.category_name
        FROM monsters m
        JOIN subcategories s ON s.subcategory_id = m.subcategory_id
        JOIN categories c ON c.category_id = s.category_id
        WHERE LOWER(m.name) IN (LOWER(${name_a}), LOWER(${name_b}))
      `;

      const a = rows.find((r) => r.name.toLowerCase() === name_a.toLowerCase());
      const b = rows.find((r) => r.name.toLowerCase() === name_b.toLowerCase());

      if (!a || !b) {
        const missing = !a ? name_a : name_b;
        return {
          content: [{
            type: "text",
            text: JSON.stringify({
              error: `Monster "${missing}" not found.`,
              source: "RAGmonsters DB · ragmonsters-server 3.4",
              next: [`list_categories({})`],
            }, null, 2),
          }],
        };
      }

      const [aAug, aHin, bAug, bHin] = await Promise.all([
        sql<Affinity[]>`SELECT target_name, modifier FROM augments WHERE monster_id = ${a.monster_id}`,
        sql<Affinity[]>`SELECT target_name, modifier FROM hindrances WHERE monster_id = ${a.monster_id}`,
        sql<Affinity[]>`SELECT target_name, modifier FROM augments WHERE monster_id = ${b.monster_id}`,
        sql<Affinity[]>`SELECT target_name, modifier FROM hindrances WHERE monster_id = ${b.monster_id}`,
      ]);

      // No server-side verdict. The data join above is the server's
      // contribution. The matchup judgement is for the LLM — see the
      // summary string below for the framing we hand it.

      return {
        content: [{
          type: "text",
          text: JSON.stringify({
            comparison: {
              [a.name]: {
                category: a.category_name, type: a.monster_type, habitat: a.habitat,
                rarity: a.rarity, primary_power: a.primary_power,
                augments: aAug, hindrances: aHin,
              },
              [b.name]: {
                category: b.category_name, type: b.monster_type, habitat: b.habitat,
                rarity: b.rarity, primary_power: b.primary_power,
                augments: bAug, hindrances: bHin,
              },
            },
            summary: `${a.name} (${a.category_name}, type=${a.monster_type}) vs. ${b.name} (${b.category_name}, type=${b.monster_type}). Augments listed under each monster boost it against named targets; hindrances penalise it. Assess the matchup by reading both sides — including whether each monster's augment targets describe the *other* monster, and whether each monster's hindrances are triggered by the *other* monster's type.`,
            source: "RAGmonsters DB · ragmonsters-server 3.4",
            next: [
              `get_monster_details({ name: "${a.name}" })`,
              `get_monster_details({ name: "${b.name}" })`,
            ],
          }, null, 2),
        }],
      };
    },
  );
}
```

compare_monsters({ name_a: "Thunderclaw", name_b: "Aquafrost" })

**Not two `get_monster_details` calls plus reasoning.** The LLM reaches for the right Tool because:

1. The Tool description (*"side-by-side comparison… in a single round-trip"*) matches the user's question shape.

### What the response looks like

The Tool returns a `comparison` object (both monsters' categories, types, primary powers, full augments and hindrances) plus a `summary` string that frames the matchup question for the LLM. **No `verdict` field.** Looking at the JSON in `/mcp`:

```json
{
  "comparison": {
    "Thunderclaw": { "category": "Elemental", "type": "Storm Predator",
                     "augments": [{ "target_name": "Water creatures", "modifier": 5 }, ...],
                     "hindrances": [...] },
    "Aquafrost":   { "category": "Elemental", "type": "Water/Ice hybrid",
                     "augments": [...],
                     "hindrances": [{ "target_name": "Electric creatures", "modifier": -5 }, ...] }
  },
  "summary": "Thunderclaw (Elemental, type=Storm Predator) vs. Aquafrost (Elemental, type=Water/Ice hybrid). Augments listed under each monster boost it against named targets; hindrances penalise it. Assess the matchup by reading both sides — including whether each monster's augment targets describe the *other* monster, and whether each monster's hindrances are triggered by the *other* monster's type.",
  "source": "...",
  "next": [...]
}
```

The LLM reads this and reasons: *"Thunderclaw has +5 vs. Water creatures — Aquafrost is a water/ice hybrid, so that augment fires. Aquafrost has −5 vs. Electric creatures — Thunderclaw is a storm/electric predator, so that hindrance fires. Both of those favour Thunderclaw."* And it gives the user the right answer.

### Why we did it this way

**Ask the same question three times.** The *data* is identical every time — that's the server's deterministic contribution. The LLM's *narrative* (which monster wins, why, in what wording) may vary slightly across runs because that's a judgement call. That's fine: the *facts* don't drift, only the *framing*. **The server doesn't lie about facts; the LLM doesn't have to invent them.**

Compare this to what would have happened if the server tried to compute a verdict itself. With `target_name = "Water creatures"` and Aquafrost's `category = "Elemental"`, a substring match returns nothing. Server says *"roughly even"* — and is **wrong**. The LLM, reading the same data, knows better. Forcing a verdict server-side puts the server in the position of authoritatively saying things it can't actually know.

This is the lesson the iteration teaches by example: **compute joins server-side, leave judgement to the LLM.** A Tool that consolidates two round trips into one is a real win. A Tool that also tries to compute the answer is overreach — especially when the answer requires fuzzy semantic matching against vocabularies the server doesn't actually have access to.

## Name the principles (two now, not one)

**Principle 1 — Add a verb when the use case demands it.**
In phase 3.0 you didn't have this Tool. You shouldn't have — you didn't know yet whether it was justified. After watching the LLM compose `get_monster_details + get_monster_details + reasoning` repeatedly, you knew. **That's when you add the verb.** This is the opposite of the v1 anti-pattern. v1 exposed every table because it *could*. v2 adds Tools because the use case *asks for them*.

**Principle 2 — Compute joins server-side; leave judgement to the LLM.**
When you add the verb, decide what the Tool *does* and what it *doesn't*. The Tool does the data join (one round trip instead of two; deterministic SQL across monsters + augments + hindrances). The Tool does **not** compute the verdict — because the verdict requires fuzzy matching across vocabularies the server doesn't actually understand, and a wrong deterministic verdict is worse than no verdict at all. The LLM is good at exactly this kind of semantic reasoning. Let it.

Both principles point the same direction: **design pressure flows from the use case down to the implementation, not from "what's easy to write" up to the API surface.** Use case asks for a comparison Tool → we add `compare_monsters`. The data the Tool can join cleanly is what it ships → we ship the data. The judgement is the LLM's strong suit → we leave it alone.
