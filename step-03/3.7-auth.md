# Phase 3.7 — Auth is not optional

> **Principle:** *Auth is not optional — even over stdio. The structure scales; the connection specifics arrive in v3.*
> **Time:** ~8 minutes
> **Files touched:** 2 new + several modify — `src/auth.ts` (new), every Tool/Resource/Prompt registration file (small modify)

## Why

You might think: *"I'm running this locally over stdio, who would I authenticate?"*

Wrong question. There isn't one auth question — there are **three**:

| Layer | What it gates | Today |
|---|---|---|
| **Connection** | Who can connect to the server? | OAuth 2.1 + PKCE + RFC 8707 audience-binding (spec; **out of scope for stdio**) |
| **Tool-level** | Who can call which Tools/Resources/Prompts? | **3.7 — this iteration** |
| **Data-level** | Who can see which rows? | beyond today — row-level filters per principal |

The **connection** question doesn't apply to stdio servers — whoever spawned the process is "connected." But the **tool-level** question does: *"now that you're connected, can you do everything, or only some things?"* Maybe `compare_monsters` is a heavyweight operation we only want a developer principal to call. Maybe a future write tool needs an `admin` principal. The structure for *gating* per-Tool exists today; we want to build it.

The shape of what we build here is exactly the shape v3 will plug real connection auth into. **It's the structure that scales.**

## Steps

1. Create `src/auth.ts` (full content below).
2. Add a `checkAuth(name)` guard at the top of every handler body.
3. Save — the dev terminal hot-reloads (compile feedback only; Claude Code runs its **own** spawned copy of the server).
4. Test with the default principal (`guest`) — `compare_monsters` should be denied.
5. Switch to `developer` by setting `MCP_PRINCIPAL` in `.mcp.json`'s `env` field, then restart Claude Code so it re-spawns the server with the new env. `compare_monsters` should now be allowed.

## The change

### New file — `src/auth.ts`

```typescript
// Principal + per-primitive permissions, set at server startup.
//
// The "principal" is the identity of the caller. In v2 over stdio it's an
// env var the server reads on launch (whoever spawned the process gets to
// decide who they are). In v3 this becomes a token claim — same shape,
// different source.
//
// Permission sets map principal -> allowed primitive names. Default deny:
// anything not in the principal's set returns auth_denied.

import { logCall } from "./log.ts";

const PERMISSIONS = {
  guest: new Set([
    // Read-only data access only. No compare_monsters (heavy operation).
    "search_monsters_by_category",
    "get_monster_details",
    "list_categories",
    "monsters://categories",
    "monsters://schema",
    "analyze_monster",
  ]),
  developer: new Set([
    // Everything guest has, plus compare_monsters.
    "search_monsters_by_category",
    "get_monster_details",
    "list_categories",
    "compare_monsters",
    "monsters://categories",
    "monsters://schema",
    "analyze_monster",
  ]),
} as const;

export type Principal = keyof typeof PERMISSIONS;

export function principal(): Principal {
  const fromEnv = process.env.MCP_PRINCIPAL;
  if (fromEnv && fromEnv in PERMISSIONS) {
    return fromEnv as Principal;
  }
  return "guest";
}

// Returns null if allowed, or a content envelope if denied.
// Handlers should: `const denied = checkAuth("..."); if (denied) return denied;`
export function checkAuth(name: string): { content: Array<{ type: "text"; text: string }> } | null {
  const p = principal();
  const allowed = PERMISSIONS[p].has(name);
  logCall("tool", "auth", { name, principal: p, decision: allowed ? "allow" : "deny" });

  if (allowed) return null;

  return {
    content: [{
      type: "text",
      text: JSON.stringify({
        error: `auth_denied: principal "${p}" cannot access "${name}"`,
        source: `RAGmonsters DB · ragmonsters-server 3.7`,
        next: [`list_categories({})`],
      }, null, 2),
    }],
  };
}

// Resource handlers return a different envelope shape (contents, not content).
// Small variant for Resources.
export function checkAuthResource(uri: string, name: string): {
  contents: Array<{ uri: string; mimeType: string; text: string }>;
} | null {
  const p = principal();
  const allowed = PERMISSIONS[p].has(name);
  logCall("resource", "auth", { name, principal: p, decision: allowed ? "allow" : "deny" });

  if (allowed) return null;

  return {
    contents: [{
      uri,
      mimeType: "application/json",
      text: JSON.stringify({
        error: `auth_denied: principal "${p}" cannot access "${name}"`,
      }, null, 2),
    }],
  };
}

// Prompt handlers return yet another shape (messages). One more variant.
export function checkAuthPrompt(name: string): {
  messages: Array<{ role: "user"; content: { type: "text"; text: string } }>;
} | null {
  const p = principal();
  const allowed = PERMISSIONS[p].has(name);
  logCall("prompt", "auth", { name, principal: p, decision: allowed ? "allow" : "deny" });

  if (allowed) return null;

  return {
    messages: [{
      role: "user" as const,
      content: {
        type: "text" as const,
        text: `auth_denied: principal "${p}" cannot access prompt "${name}".`,
      },
    }],
  };
}
```

### Modify — every Tool

At the top of each Tool handler, before the existing `logCall(...)`, add:

```typescript
const denied = checkAuth("tool_name_here");
if (denied) return denied;
```

For example, `compare_monsters`:

```typescript
async ({ name_a, name_b }) => {
  const denied = checkAuth("compare_monsters");
  if (denied) return denied;

  const start = Date.now();
  logCall("tool", "compare_monsters", { name_a, name_b });
  // ... rest of handler unchanged
}
```

Don't forget the import:

```typescript
import { checkAuth } from "../auth.ts";
```

Repeat for each Tool: `search_monsters_by_category`, `get_monster_details`, `list_categories`, `compare_monsters`.

### Modify — Resources

Resources use `checkAuthResource(uri.href, "resource://name")`. Example for `monsters://categories`:

```typescript
async (uri) => {
  const denied = checkAuthResource(uri.href, "monsters://categories");
  if (denied) return denied;

  const start = Date.now();
  logCall("resource", "monsters://categories", { uri: uri.href });
  // ... rest of handler unchanged
}
```

Repeat for `monsters://schema`.

### Modify — Prompts

Prompts use `checkAuthPrompt("prompt_name")`. Example for `analyze_monster`:

```typescript
async ({ monster_name }) => {
  const denied = checkAuthPrompt("analyze_monster");

}
```

## Observe

> **Heads-up — two server processes.** Your `bun --hot run` dev terminal is **not** the server Claude Code talks to. Claude Code spawns its **own** copy of `src/server.ts` per `.mcp.json` (with its own env), and that process's stderr is invisible to you. That's exactly why we built `src/log.ts` to write to `logs/server.log` in 3.0 — the log file is our shared observation surface across both processes.
>
> Open a **third terminal** and tail the log:
>
> ```bash
> tail -f logs/server.log
> ```
>
> Leave it visible alongside the dev terminal. The dev terminal tells you "did my code compile?"; the log tells you "what did Claude Code's server actually do?".

### Part 1 — Default principal (`guest`)

`.mcp.json` has no `env` block (or `MCP_PRINCIPAL` is unset) → `principal()` returns `"guest"`. If you have a Claude Code session already open from a prior iteration, restart it now so it re-spawns the server with the new code.

In Claude Code, ask: *"Compare Thunderclaw and Aquafrost."*

In your tailed `logs/server.log`:

```

```

The LLM receives `{error: "auth_denied: principal \"guest\" cannot access \"compare_monsters\"", next: ["list_categories({})"]}`. It tells you something like: *"I can't compare monsters as a guest — but I can list categories. Want to start there?"* (Exact wording varies.)

### Part 2 — Developer principal

Env vars exported into your dev-terminal shell do **not** reach Claude Code's spawned server. To switch principals, set the env in `.mcp.json`:

```json
{
  "mcpServers": {
    "ragmonsters": {
      "command": "bun",
      "args": ["run", "src/server.ts"],
      "env": {
        "MCP_PRINCIPAL": "developer"
      }
    }
  }
}
```

Save, then **restart Claude Code** (quit and re-launch the session) so it re-spawns the server picking up the new env block. The dev terminal needs no change.

Same prompt: *"Compare Thunderclaw and Aquafrost."*

In `logs/server.log`:

```
[2026-05-19T11:51:14.456Z] tool=auth args={"name":"compare_monsters","principal":"developer","decision":"allow"}
[2026-05-19T11:51:14.461Z] tool=compare_monsters args={"name_a":"Thunderclaw","name_b":"Aquafrost"}
[2026-05-19T11:51:14.498Z] result=compare_monsters compared a="Thunderclaw" b="Aquafrost" augments=2/3 hindrances=1/2 37ms

Same code. Same data. Different principal — different behaviour. The decision is per-call, per-principal, logged.

## Honest framing

Stdio doesn't authenticate the *principal* in any cryptographic sense. Anybody who spawned the server gets to set `MCP_PRINCIPAL`. **That's intentional for this phase.** What we built is the **shape** — the structure that lets you plug real auth in later without changing the rest of the server.

In v3, you replace `principal()` with a function that reads the OAuth token's audience claim (RFC 8707). The `checkAuth()` call sites don't change. **That's why the structure scales.**

## Real-life note

Production auth has more knobs:

- **Multi-claim permissions.** A principal often carries multiple claims (org membership, role, scopes). Permission checks become predicates, not set membership.
- **Audit trail.** Every `decision: "allow"` and `decision: "deny"` lands in a tamper-evident log (append-only, signed). Compliance frameworks ask for this.
- **Time-bound tokens.** Tokens expire. `checkAuth` re-validates the token on every call (or at minimum, on a TTL).
- **Per-resource policies.** A real RBAC system would have policies like *"developers can read all monsters but only update their own."* That's data-level auth — the third row in the table above.

The shape stays the same: every call → through a gate → into the handler. The gate consults more sophisticated policy; the gate's place in the architecture doesn't move.

## Common gotchas (phase 3.7)

| Symptom | Likely cause | Fix |
|---|---|---|
| Every call returns `auth_denied` even after setting `MCP_PRINCIPAL=developer` | You exported the env var in your dev-terminal shell, but Claude Code spawns its own server process and never sees that export | Put `MCP_PRINCIPAL` in `.mcp.json`'s `env` field, then **restart Claude Code** so it re-spawns the server with the new env |
| Dev terminal shows the recompile but `logs/server.log` is silent for the call | You're reading the wrong process — `bun --hot` is your dev terminal, Claude Code runs its own copy | Tail `logs/server.log`; that's the surface both processes write to |
| `checkAuth` returns null but the handler returns an unrelated error | The order is wrong — you put `checkAuth` after some other logic that errored first | Move `checkAuth` to the very first line of the handler |
| TypeScript complains the return shape doesn't match the handler's expected return | You're using `checkAuth` (Tool shape) in a Resource handler | Use the right helper: `checkAuthResource` for Resources, `checkAuthPrompt` for Prompts |
| Logging shows `decision: "deny"` for a primitive you expected to be allowed | The name string doesn't match the PERMISSIONS set entry | Match `name` exactly to the entry in `PERMISSIONS` |
| Want to add a third principal | Add a key + Set entries to `PERMISSIONS`. The `Principal` type derives automatically. | One-liner |
