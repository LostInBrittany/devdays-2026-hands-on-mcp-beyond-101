# Phase 3.6 — Validate every input. Sanitize every output.

> **Principle:** *Outputs from your MCP server are inputs to your LLM. Treat them as untrusted data.*
> **Time:** ~12 minutes
> **Files touched:** 3 — `src/sanitize.ts` (new), `src/tools/get-monster-details.ts` (modify), `src/tools/compare-monsters.ts` (modify)

## Why

You've Zod-validated every **input** since 3.0. That's half the picture.

The other half is what comes *out* of your handlers. Right now `get_monster_details` returns whatever the DB gives back — including the `notable_specimens` free-text column. The LLM reads that text. The LLM trusts that text. **If anything ever lands in that column that looks like an instruction, the LLM is going to read it as one.**

This isn't theoretical. It's the same bug class as SQL injection, just at a different layer:

| Bobby Tables (SQL injection) | Billy Ignore (output prompt injection) |
|---|---|
| input → SQL string → DB executes | DB string → tool response → LLM "executes" |
| fixed by parameterised queries (you did this in 3.0) | fixed by sanitising **outputs** before returning |
| 25-year-old bug | new family — same shape, new layer |

A row could be poisoned for many reasons: a bad data import, an attacker who once had `INSERT` access, a scraping pipeline that pulled from an untrusted source. **You don't get to assume your DB content is trustworthy when the LLM is reading it.**

Two coordinated moves in this phase:

1. **Sanitize outputs** — scrub the free-text fields before returning them. A small helper that replaces well-known injection markers.
2. **Validate outputs** — add a Zod schema for the *return* shape of `get_monster_details`. Parse the data through it before sending. Catches schema drift; documents the contract.

**Principle:** *Outputs from your MCP server are inputs to your LLM. Treat them as untrusted data.*

## The change

### New file — `src/sanitize.ts`

```typescript
// Output sanitisation — the "outputs are inputs" defence.
//
// The LLM treats tool-response text as instructions. If any free-text field
// in our response contains an instruction prefix ("ignore previous...",
// "system:", "assistant:"), it could change the LLM's behaviour. We scrub
// those markers before returning anything to the client.
//
// This is a deliberately small allowlist of patterns. Production code would
// expand it, possibly with regex packs / classifier calls. For 3.6 the point
// is the pattern, not exhaustive coverage.

import { logCall } from "./log.ts";

const INJECTION_PATTERNS: { pattern: RegExp; label: string }[] = [
  { pattern: /\bignore\s+(all\s+)?previous\s+instructions?\b/gi, label: "ignore-previous" },
  { pattern: /\b(system|assistant|user)\s*:/gi,                  label: "role-prefix"    },
  { pattern: /<\|im_(start|end)\|>/gi,                           label: "chat-template"  },
  { pattern: /\[INST\]|\[\/INST\]/gi,                            label: "inst-tags"      },
  { pattern: /reveal\s+(your\s+)?system\s+prompt/gi,             label: "prompt-leak"    },
];

export function sanitizeText(text: string, fieldName: string): string {
  if (!text) return text;

  let sanitized = text;
  const hits: string[] = [];

  for (const { pattern, label } of INJECTION_PATTERNS) {
    if (pattern.test(sanitized)) {
      hits.push(label);
      sanitized = sanitized.replace(pattern, "[REDACTED]");
    }
  }

  if (hits.length > 0) {
    logCall("tool", "sanitize", {
      field: fieldName,
      patterns_matched: hits,
      original_length: text.length,
    });
  }

  return sanitized;
}
```

### Modify — `src/tools/get-monster-details.ts`

Add one import (you already have `z` from 3.0):

```typescript
import { sanitizeText } from "../sanitize.ts";
```

Define an **output schema** at the top of the file (after the imports). The shape mirrors the JSON envelope this tool already returns since 3.2 — `data` plus `summary`, `source`, `next`. Adding the schema makes the contract explicit and rejects drift.

```typescript
// What we promise to return. If the DB gives us something that doesn't fit,
// we'd rather log + return an error than confuse the LLM with a malformed
// response. Strict — extra fields rejected at every level.
const monsterDetailsOutput = z.object({
  data: z.object({
    name: z.string(),
    monster_type: z.string(),
    habitat: z.string(),
    biome: z.string(),
    rarity: z.string(),
    height: z.string(),
    weight: z.string(),
    appearance: z.string(),
    primary_power: z.string(),
    secondary_power: z.string(),
    special_ability: z.string(),
    weakness: z.string(),
    behavior_ecology: z.string(),
    notable_specimens: z.string(),
    category_name: z.string(),
  }).strict(),
  summary: z.string(),
  source: z.string(),
  next: z.array(z.string()),
}).strict();
```

Now modify the handler body. The two new moves are: (1) sanitize the four free-text fields before they enter the envelope; (2) parse the envelope through the output schema before returning. The SELECT, the JOIN to `categories`, the envelope shape — all unchanged from 3.5.

```typescript
async ({ name }) => {
  const start = Date.now();
  logCall("tool", "get_monster_details", { name });

  // SELECT, JOIN, envelope: all unchanged from 3.5.
  const rows = await sql<
    {
      name: string; monster_type: string; habitat: string; biome: string;
      rarity: string; height: string; weight: string; appearance: string;
      primary_power: string; secondary_power: string; special_ability: string;
      weakness: string; behavior_ecology: string; notable_specimens: string;
      category_name: string;
    }[]
  >`
    SELECT
      m.name, m.monster_type, m.habitat, m.biome, m.rarity,
      m.height, m.weight, m.appearance,
      m.primary_power, m.secondary_power, m.special_ability,
      m.weakness, m.behavior_ecology, m.notable_specimens,
      c.category_name
    FROM monsters m
    JOIN subcategories s ON s.subcategory_id = m.subcategory_id
    JOIN categories c ON c.category_id = s.category_id
    WHERE LOWER(m.name) = LOWER(${name})
    LIMIT 1
  `;

  if (rows.length === 0) {
    logResult(
      "get_monster_details",
      `not_found name="${name}"`,
      Date.now() - start,
    );
    return {
      content: [{
        type: "text",
        text: JSON.stringify(
          {
            error: `Monster "${name}" not found.`,
            source: "RAGmonsters DB · ragmonsters-server 3.6",
            next: [`list_categories({})`],
          },
          null,
          2,
        ),
      }],
    };
  }

  const m = rows[0]!;

  // NEW in 3.6 — sanitize the four free-text fields before they hit the LLM.
  // Bounded enum-ish fields (monster_type, category_name, habitat, biome,
  // rarity, height, weight) don't need sanitisation — they're constrained by
  // the data model.
  const sanitized = {
    ...m,
    appearance:        sanitizeText(m.appearance,        "appearance"),
    weakness:          sanitizeText(m.weakness,          "weakness"),
    behavior_ecology:  sanitizeText(m.behavior_ecology,  "behavior_ecology"),
    notable_specimens: sanitizeText(m.notable_specimens, "notable_specimens"),
  };

  // Build the envelope first, then validate the whole thing. If the DB ever
  // returns something off-shape, we'd rather return an error than confuse
  // the LLM with malformed JSON.
  const envelope = {
    data: sanitized,
    summary: `${sanitized.name} — ${sanitized.rarity} ${sanitized.monster_type} from ${sanitized.habitat} (${sanitized.category_name}).`,
    source: "RAGmonsters DB · ragmonsters-server 3.6",
    next: [
      `search_monsters_by_category({ category: "${sanitized.category_name}", limit: 10 })`,
    ],
  };

  const parsed = monsterDetailsOutput.safeParse(envelope);
  if (!parsed.success) {
    logResult(
      "get_monster_details",
      `output_validation_fail name="${m.name}"`,
      Date.now() - start,
    );
    return {
      content: [{
        type: "text",
        text: JSON.stringify({
          error: "Server response did not match expected schema.",
          source: "RAGmonsters DB · ragmonsters-server 3.6",
          next: [`search_monsters_by_category({ category: "Elemental" })`],
        }, null, 2),
      }],
    };
  }

  logResult(
    "get_monster_details",
    `found name="${m.name}"`,
    Date.now() - start,
  );

  return {
    content: [{
      type: "text",
      text: JSON.stringify(parsed.data, null, 2),
    }],
  };
},
```

### Modify — `src/tools/compare-monsters.ts`

This Tool returns `augments` and `hindrances` arrays. Each row has a `target_name` string drawn from the DB. Apply sanitisation to those before constructing the response.

Add the import:

```typescript
import { sanitizeText } from "../sanitize.ts";
```

In the handler, just before constructing the response:

```typescript
// Sanitise free-text target_name values from augments/hindrances.
const sanitize = (arr: Affinity[], fieldPrefix: string): Affinity[] =>
  arr.map((row) => ({
    ...row,
    target_name: sanitizeText(row.target_name, `${fieldPrefix}.target_name`),
  }));

const aAugS = sanitize(aAug, "a.augments");
const aHinS = sanitize(aHin, "a.hindrances");
```

## Real-life note

What we built is a **deliberately minimal** sanitiser: 5 regex patterns and `[REDACTED]` replacement. Production sanitisation is more elaborate:

- **More patterns.** Every chat template format, every known jailbreak phrase, every role-injection variant. Open-source pattern packs exist (see e.g. `prompt-injection-detector` projects).
- **Classifier-based detection.** A small fine-tuned model classifying "this looks like an injection attempt" — slower but catches paraphrases the regex misses.
- **Field-level policy.** Some fields can be fully suppressed; others get a soft-flag attached so the LLM knows *something* was there but not what.
- **Output token logging.** Hash + truncate before logging — the redaction event is auditable but the original payload isn't preserved in plain text.

The shape stays the same: every piece of free text out → through a gate → into the response. The gate gets smarter; the gate's place in the architecture doesn't move.

## Common gotchas (phase 3.6)

| Symptom | Likely cause | Fix |
|---|---|---|
| Output schema rejects valid data | Schema is stricter than the DB column allows (e.g., a real NULL where the schema requires string) | Loosen the Zod schema for that field (`.nullable()` or `.optional()`) |
| `sanitizeText` doesn't fire on the poisoned string | The injection text doesn't match any pattern | Add a regex to `INJECTION_PATTERNS`. The patterns are a known-list — expand them per attack vector |
| `bun run scripts/poison-thunderclaw.ts` fails | `pglite/`'s `start:pg` isn't running, or PGlite is held by another client | Restart `pglite/`'s `start:pg` and close any other Claude Code session holding the slot |
| Sanitized text breaks markdown rendering | `[REDACTED]` is plain text and renders fine; if you used special chars, that'd be a problem | Use plain `[REDACTED]` — works everywhere |
| Output validation fails on `monster_id` | You probably forgot `.strict()` and an extra field appeared; or you forgot to drop the field in your SELECT | Match the schema to your SQL selection list exactly |
