# Phase 3.2 — `next` hypermedia + pagination

> **Principle:** *Tell the LLM what to do next.*
> **Time:** ~12 minutes
> **Files touched:** 3 — all three Tool files in `src/tools/`

## Why

After phase 3.1, the LLM gets bounded, typed answers — but they're **flat**. A Tool returns "here's 10 monsters" and stops. The LLM has to guess what to do next:

- *"Should I look at the first one?"*
- *"Should I search again with a different category?"*
- *"Was there more, or did I get everything?"*

Every guess is a chance to misroute. Every wrong guess is at least one wasted turn (often two — the wrong tool call plus the recovery).

REST faced this problem twenty years ago. Roy Fielding's PhD thesis named the answer **HATEOAS** — *Hypermedia As The Engine Of Application State*. Bluntly: **the server's response tells the client what to do next.** A search response includes a link to the next page, a link to filter, a link to the first result's detail page. The client doesn't construct those — it follows them.

For MCP, the same idea applies. Every Tool response can include a `next` field that suggests follow-up tool calls. The LLM doesn't have to invent the next step; the server already knows what makes sense after a search.

There's a second thing we'll fix at the same time: **pagination.** `search_monsters_by_category` currently has a `limit` parameter but no `offset`. If there are 12 Elemental monsters and the LLM asks for 10, the LLM has no way to know there are 2 more. We add `offset`, and the response tells the LLM how to fetch the next page via `next`.

## The change

### Modify — `src/tools/search-monsters-by-category.ts`

Add `offset` to the `inputSchema`:

```typescript
inputSchema: {
  category: z.enum(CATEGORIES),
  limit: z.number().int().min(1).max(50).optional().default(10),
  offset: z.number().int().min(0).optional().default(0),   // ← NEW in 3.2
},
```

Replace the handler body:

```typescript
async ({ category, limit, offset }) => {
  const start = Date.now();
  logCall("tool", "search_monsters_by_category", { category, limit, offset });

  const rows = await sql<
    { name: string; monster_type: string; habitat: string; rarity: string }[]
  >`
    SELECT m.name, m.monster_type, m.habitat, m.rarity
    FROM monsters m
    JOIN subcategories s ON s.subcategory_id = m.subcategory_id
    JOIN categories c ON c.category_id = s.category_id
    WHERE c.category_name = ${category}
    ORDER BY m.name
    LIMIT ${limit} OFFSET ${offset}
  `;

  const [{ total }] = await sql<{ total: number }[]>`
    SELECT count(*)::int AS total
    FROM monsters m
    JOIN subcategories s ON s.subcategory_id = m.subcategory_id
    JOIN categories c ON c.category_id = s.category_id
    WHERE c.category_name = ${category}
  `;

  const hasMore = offset + rows.length < total;
  const next: string[] = [];

  // Hint 1 — pagination: if there are more, suggest the next page.
  if (hasMore) {
    next.push(
      `search_monsters_by_category({ category: "${category}", limit: ${limit}, offset: ${offset + limit} })`,
    );
  }

  // Hint 2 — drill-down: if we got at least one row, suggest its details.
  if (rows.length > 0) {
    next.push(`get_monster_details({ name: "${rows[0]!.name}" })`);
  }

  // Hint 3 — pivot: forward-compatible reference to compare_monsters (phase 3.4).
  if (rows.length >= 2) {
    next.push(
      `compare_monsters({ name_a: "${rows[0]!.name}", name_b: "${rows[1]!.name}" })`,
    );
  }

  logResult(
    "search_monsters_by_category",
    `found=${rows.length}/${total} next=${next.length}`,
    Date.now() - start,
  );

  return {
    content: [{
      type: "text",
      text: JSON.stringify(
        {
          data: rows,
          summary: `Found ${rows.length} of ${total} monsters in category "${category}"${hasMore ? " (more available — see `next`)" : ""}.`,
          source: "RAGmonsters DB · ragmonsters-server 3.2",
          next,
        },
        null,
        2,
      ),
    }],
  };
},
```

(The `logCall` / `logResult` imports came in at 3.0 and stay imported — same `import { logCall, logResult } from "../log.ts"` line at the top of the file.)

### Modify — `src/tools/get-monster-details.ts`

Two moves on top of 3.0/3.1: **add** the JOIN to `categories` (so the response can tell the LLM which category this monster belongs to, and hand back a `next` link to peers), and **wrap** the response in the same `{data, summary, source, next}` hypermedia envelope you just built for `search_monsters_by_category`. Every field 3.0 returned stays in the SELECT — features accumulate.

Replace the handler body:

```typescript
async ({ name }) => {
  const start = Date.now();
  logCall("tool", "get_monster_details", { name });

  const rows = await sql<
    {
      name: string; monster_type: string; habitat: string; biome: string;
      rarity: string; height: string; weight: string; appearance: string;
      primary_power: string; secondary_power: string; special_ability: string;
      weakness: string; behavior_ecology: string; notable_specimens: string;
      category_name: string;
    }[]
  >`
    SELECT
      m.name, m.monster_type, m.habitat, m.biome, m.rarity,
      m.height, m.weight, m.appearance,
      m.primary_power, m.secondary_power, m.special_ability,
      m.weakness, m.behavior_ecology, m.notable_specimens,
      c.category_name
    FROM monsters m
    JOIN subcategories s ON s.subcategory_id = m.subcategory_id
    JOIN categories c ON c.category_id = s.category_id
    WHERE LOWER(m.name) = LOWER(${name})
    LIMIT 1
  `;

  if (rows.length === 0) {
    logResult(
      "get_monster_details",
      `not_found name="${name}"`,
      Date.now() - start,
    );
    return {
      content: [{
        type: "text",
        text: JSON.stringify(
          {
            error: `Monster "${name}" not found.`,
            source: "RAGmonsters DB · ragmonsters-server 3.2",
            next: [`list_categories({})`],
          },
          null,
          2,
        ),
      }],
    };
  }

  const m = rows[0]!;
  logResult(
    "get_monster_details",
    `found name="${m.name}"`,
    Date.now() - start,
  );

  return {
    content: [{
      type: "text",
      text: JSON.stringify(
        {
          data: m,
          summary: `${m.name} — ${m.rarity} ${m.monster_type} from ${m.habitat} (${m.category_name}).`,
          source: "RAGmonsters DB · ragmonsters-server 3.2",
          next: [
            `search_monsters_by_category({ category: "${m.category_name}", limit: 10 })`,
          ],
        },
        null,
        2,
      ),
    }],
  };
},
```

(The markdown text formatter from 3.0 is gone — the JSON envelope replaces it. The client renders the `data` payload however it wants; what matters is that *every* response — list, get, error — now has the same shape with `summary`/`source`/`next`. That's the hypermedia.)

### Modify — `src/tools/list-categories.ts`

Replace the handler body:

```typescript
async () => {
  const start = Date.now();
  logCall("tool", "list_categories", {});

  const rows = await sql<{ category_name: string; description: string }[]>`
    SELECT category_name, description FROM categories ORDER BY category_name
  `;

  logResult("list_categories", `count=${rows.length}`, Date.now() - start);

  return {
    content: [{
      type: "text",
      text: JSON.stringify(
        {
          data: rows,
          summary: `${rows.length} categories available.`,
          source: "RAGmonsters DB · ragmonsters-server 3.2",
          next: rows.map(
            (r) => `search_monsters_by_category({ category: "${r.category_name}" })`,
          ),
        },
        null,
        2,
      ),
    }],
  };
},
```

## Observe

**Run all three observations.** The contrast between them is the lesson — not any single trace.

### Observation 1a — when the hint fires (mechanical prompt)

In Claude Code:

> *"Find three Elemental monsters and then get details on the first result."*

Watch the `/mcp` trace. You should see two tool calls:

1. `search_monsters_by_category({ category: "Elemental", limit: 3 })` — returns `data` + `next` (with a `get_monster_details` suggestion).
2. `get_monster_details({ name: "<first row from step 1>" })` — **the LLM follows the `next[0]` hint.** It didn't have to invent the name; the server suggested.

The user's prompt (*"the first result"*) aligns with the server's hint (`get_monster_details` on `rows[0]`). When user intent and server suggestion point the same way, the hint is the path of least resistance and the LLM takes it.

### Observation 1b — when the hint gets *ignored* (subjective prompt)

Same conversation, follow-up prompt:

> *"Now find Elemental monsters and tell me about the most interesting one."*

Watch the trace. You will probably see something like:

1. `search_monsters_by_category({ category: "Elemental" })` — returns 8 rows + `next[0] = get_monster_details({ name: "Abyssalurk" })` (just the alphabetically-first monster).
2. `get_monster_details({ name: "Magmawraith" })` — **the LLM ignored the hint** and picked its own monster.
3. Possibly 1–2 more `get_monster_details` calls on other monsters, as the LLM samples to support its judgement.

**This is not a bug. This is the lesson.**

The `next` array is **advisory text** — nothing in the MCP spec defines it. Claude Code injects the response text into the LLM's context verbatim; the LLM reads the suggestion the same way it reads the rest of the JSON, weighs it against the user's prompt, and decides. When the user asks for *"the most interesting one,"* the model exercises judgement — *"Abyssalurk because it's alphabetically first"* is not what the user asked for, so the LLM overrides the hint with its own pick.

**Tie back to 3.1 Beat 2.** In 3.1 we hit the **application-controlled** tier — the host decides whether to surface a Resource. Here we're hitting the **model-controlled** tier — the LLM decides whether to follow a hint. Two different gaps between *publishing* and *consuming*, same underlying principle: **the server's job is to publish correctly; whether anyone listens is the next tier's problem.**

### Observation 2 — when `next` is the path of least resistance (pagination)

> *"Show me the Elemental monsters, but only 3 at a time. Walk through all of them."*

The RAGmonsters dataset is small — the biggest category (`Elemental`) has 8 monsters, so the default `limit: 10` would return them all in one page and never trigger pagination. Forcing `limit: 3` in the prompt above is what makes the demo fire.

Watch the `/mcp` trace. You should see roughly:
1. `search_monsters_by_category({ category: "Elemental", limit: 3 })` → returns 3 of 8, `next` includes `offset: 3`.
2. `search_monsters_by_category({ category: "Elemental", limit: 3, offset: 3 })` → returns 3 of 8, `next` includes `offset: 6`.
3. `search_monsters_by_category({ category: "Elemental", limit: 3, offset: 6 })` → returns 2 of 8, **no `offset:` hint in `next`** because `hasMore` is false.

The LLM follows the `next` hint three times. **No counting, no trial-and-error.**

**Why does pagination fire reliably when 1b didn't?** Because there's no judgement to exercise. *"Walk through all of them"* has exactly one mechanical interpretation, and the server's `next` is the cheapest path to it. The LLM has nothing better to invent — so it follows.

### Honest aside

Different agentic clients consume `next` differently, and even the *same* client behaves differently depending on prompt:

- **Mechanical prompts** (*"get details on the first result"*, *"walk through all"*) → the hint reliably fires. The LLM has no reason to deviate.
- **Subjective prompts** (*"the most interesting"*, *"a good example"*) → the hint gets weighed against the model's own judgement and is often overridden. The model-controlled tier expressing itself.
- **Some other agents** treat the response as opaque text and ignore the `next` array entirely even on mechanical prompts. The LLM still benefits (it reads the suggestion in plain text and may repeat the call) — but the *automation* depends on the client.

**That asymmetry is not a bug to fix in v2.** v2's job is to **publish the hint correctly** — which it does, in every response, regardless of who's reading. Whether it gets consumed is a property of the application and model tiers. Designing servers in spite of that gap is the workshop's whole thesis.

## Why this is the most portable v2 pattern

You added ~40 lines of code, and on mechanical prompts the LLM's reasoning got measurably shorter. Before: "search, look at results, decide which to fetch, build the args." After: "search, follow the hint." Same outcome, fewer decisions, fewer chances to misroute — *when the prompt is mechanical.*

On subjective prompts the LLM will still exercise judgement, and that's fine. The hint costs nothing when ignored. The hint pays off every time it's followed. **Asymmetric upside.** That's what makes `next` worth shipping even though no client is contractually obliged to consume it.

**This pattern transfers beyond MCP.** Any LLM tool surface — function-calling, agent frameworks, even chat plugins — benefits from response envelopes that suggest follow-up calls. **You'll use this everywhere from now on.**

## Common gotchas (phase 3.2)

| Symptom | Likely cause | Fix |
|---|---|---|
| `offset` not recognized as a parameter | Forgot to add it to `inputSchema` | Add `offset: z.number().int().min(0).optional().default(0)` to the inputSchema block |
| Claude Code calls the Tool but doesn't follow `next` | Client cached the old tool definition | `/mcp` to re-list, or restart Claude Code |
| `next` contains a `compare_monsters` call but it fails | `compare_monsters` doesn't exist yet — it lands in phase 3.4 | Expected; the hint is forward-compatible. The LLM will skip it gracefully, or you can ignore the error |
| The response is harder to read in the Claude Code UI | Returning JSON.stringify text instead of plain markdown | Cosmetic; the *structure* is the point. The LLM parses it fine. |
| TypeScript error about `rows[0]` possibly undefined | Strict null checks | Use the non-null assertion `rows[0]!` since we've just checked `rows.length > 0` |
