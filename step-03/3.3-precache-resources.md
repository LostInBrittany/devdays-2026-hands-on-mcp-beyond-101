# Phase 3.3 — Pre-cache Resources at server init

> **Principle:** *If you say "cacheable," make it cacheable.*
> **Time:** ~8 minutes
> **Files touched:** 4 — `src/cache.ts` (new), `src/log.ts` (modify — new `logEvent` export), `src/server.ts` (modify), `src/resources/monsters-categories.ts` (modify)

## Why

Look at your phase 3.0 / 3.1 implementations of `monsters://categories` and `monsters://schema`. Read the description fields out loud:

- `"All monster categories with their descriptions. Static-ish; **cacheable**."` (categories)
- `"Read this first to understand what Tools to reach for."` (schema — static text, never queries DB)

Now look at the handler bodies. The categories Resource **runs a SQL query every single time the LLM reads it.** The description promises something the code doesn't deliver.

The slide deck for this module is going to say *"Resources are cacheable facts."* If we ship code that doesn't cache them, we're teaching the wrong lesson — that Resources are *theoretically* cacheable while actually being indistinguishable from Tools.

The fix is small. For bounded, slow-changing data:

1. **Load the data once**, at server startup, before `server.connect()`.
2. **Store it in a module-level variable** (or a `Cache` object).
3. **Resource handlers read from memory**, not from the DB.

The trade-off is real and worth naming: **cache invalidation is a cost.** If the underlying categories change while the server is running, the Resource is stale until restart. For our case — six categories, hand-curated in the seed, never changes during a workshop — that's fine. **For per-monster details (which could change every minute in a real system), pre-caching would be wrong.** The principle isn't "cache everything" — it's "cache what your data model says is safe to cache."

## The change

### New file — `src/cache.ts`

```typescript
// Module-level cache for bounded, slow-changing Resource data.
//
// 3.3 design choice — what to cache:
//   - `categories`     — 6 rows, hand-curated in seed, never changes during a session
//   - `subcategories`  — ~12 rows, same stability profile
//
// What we do NOT cache here:
//   - Per-monster details — change frequency unknown, treat as live
//   - Search results — depend on input parameters, not cacheable as a unit

import { sql } from "./db.ts";
import { logEvent } from "./log.ts";

type CategoryRow = { category_name: string; description: string };
type SubcategoryRow = { subcategory_name: string; category_name: string };

let cachedCategories: CategoryRow[] | null = null;
let cachedSubcategories: SubcategoryRow[] | null = null;

export async function initializeCache(): Promise<void> {
  const t0 = Date.now();
  logEvent("cache=init starting");

  cachedCategories = await sql<CategoryRow[]>`
    SELECT category_name, description
    FROM categories
    ORDER BY category_name
  `;

  cachedSubcategories = await sql<SubcategoryRow[]>`
    SELECT s.subcategory_name, c.category_name
    FROM subcategories s
    JOIN categories c ON c.category_id = s.category_id
    ORDER BY c.category_name, s.subcategory_name
  `;

  logEvent(
    `cache=init done categories=${cachedCategories.length} subcategories=${cachedSubcategories.length} ${Date.now() - t0}ms`,
  );
}

export function getCachedCategories(): CategoryRow[] {
  if (!cachedCategories) {
    throw new Error("Cache not initialized. Call initializeCache() before reading.");
  }
  return cachedCategories;
}

export function getCachedSubcategories(): SubcategoryRow[] {
  if (!cachedSubcategories) {
    throw new Error("Cache not initialized. Call initializeCache() before reading.");
  }
  return cachedSubcategories;
}
```

### Modify — `src/log.ts`

The existing logger only knows about *primitive calls* (`logCall`, `logResult`). Cache initialization isn't a primitive — it's a server-lifecycle event. We want it in `logs/server.log` next to everything else so participants tailing the log can *see* the cache populate, but we don't want to overload `logCall` with a fake primitive name like `"cache"`.

Add a small `logEvent` export at the bottom of `src/log.ts`:

```typescript
// Server-lifecycle events (cache init, future: cache reload, auth init, etc.).
// Not a primitive call — separate channel so traces stay legible.
export function logEvent(message: string): void {
  const ts = new Date().toISOString();
  emit(`[${ts}] ${message}`);
}
```

(Why `emit`? It's the private helper already in `log.ts` that writes to **both** sinks — `logs/server.log` *and* stderr. Using `console.error` directly would skip the file sink and the message wouldn't reach the participant's `tail -f` terminal — which is the whole point of this exercise.)

### Modify — `src/server.ts`

Add the import:

```typescript
import { initializeCache } from "./cache.ts";
```

Before `server.connect(transport)`, add the initialization:

```typescript
// Pre-cache bounded Resources before connecting.
// (If this throws, the server won't connect — that's correct;
//  a server with broken cache is worse than no server.)
await initializeCache();

// stdio transport — Claude Code spawns this process and talks to us over stdin/stdout.
const transport = new StdioServerTransport();
await server.connect(transport);
```

### Modify — `src/resources/monsters-categories.ts`

Replace the SQL-querying handler with a cache read:

```typescript
import type { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";

import { getCachedCategories } from "../cache.ts";

export function registerMonstersCategoriesResource(server: McpServer) {
  server.registerResource(
    "monsters-categories",
    "monsters://categories",
    {
      description: "All monster categories with descriptions. Cached at server init.",
      mimeType: "application/json",
    },
    async (uri) => ({
      contents: [{
        uri: uri.href,
        mimeType: "application/json",
        text: JSON.stringify(getCachedCategories(), null, 2),     // ← memory read, no SQL
      }],
    }),
  );
}
```

Notice you can now remove the `import { sql } from "../db.ts";` line from this file — it's no longer used here.

### Name the trade-off — and the scope

What just happened is the workshop's first explicit caching decision. Name it for yourself:

> *"I made a deliberate freshness vs. speed trade-off. Categories don't change during the workshop, so caching is safe and free. Per-monster details might change — so I did NOT cache them. The principle is to **let the data model decide what's cacheable**, not 'cache everything we can.'"*

**But also name what this cache is *not* doing.** This is the part the slide deck conveniently elides. The cache lives **inside the server process**. It changes one thing only — the latency of a `ReadResource` call when the client *does* read.

| Concern | Solved by | What 3.3 does about it |
|---|---|---|
| "When the client reads the Resource, is it slow because of a DB query?" | **Server-side caching (this iteration).** | Replaces the DB query with a memory read. |
| "How often does Claude Code re-read the Resource?" | Application-controlled tier — `instructions` (3.1 Beat 2), tool descriptions referencing the Resource, `next` hints in 3.2. | Nothing. Out of scope. |
| "If the underlying data changes, how does the client find out?" | `notifications/resources/updated` (server-pushed). Client must subscribe and honour. Patchy support in practice. | Nothing. Not addressed. |

**If Claude Code doesn't re-read `monsters://categories`, the cache never fires for that conversation.** That's not a caching bug — it's the application-controlled tier again. The cache only pays off in conversations where the client *does* read repeatedly: long sessions, many tool calls, or future iterations that pre-fetch on a `next` hint. Caching is about *making reads cheap when they happen*, not about *making them happen more often.*

## Bonus observation: the schema Resource was already cached

Look at your `src/resources/schema.ts` from phase 3.1. The body is a `const string`. **It was already cached** — read from memory the whole time, no `cache.ts` needed. **Static data is automatically pattern (1).** 3.3 extends pattern (1) to dynamic-but-bounded data (categories you happen to load from a DB but that won't change).

## Tie back: the three control tiers, one iteration at a time

3.1 Beat 2 hit the **application-controlled tier** — Resources surfaced or not by host policy.
3.2 hit the **model-controlled tier** — `next` hints followed or not by LLM judgement.
3.3 stays squarely on the **server tier** — what you control inside your own process. The cache is *yours.* The latency win is *yours.* The freshness budget is *yours.* What the client does with the result is its problem.

That's the honest framing: **don't oversell what server-side caching does, and don't undersell it either.** It's the cheapest, most reliable optimization you have on this surface. It just isn't the answer to every freshness question.
