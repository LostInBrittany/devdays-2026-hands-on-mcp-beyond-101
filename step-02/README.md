# Step 02 — First rung: "it works" (and it's broken)

> The official MCP server for Postgres that Anthropic shipped in 2024 — and archived in 2025.
> We install it from npm, point it at a real Postgres, and watch it bite.

**Time:** ~80 minutes
**Maturity rung:** v1 — *MCP works*
**Goal:** feel — in your own terminal — what was wrong with the first generation of MCP servers.

## What you'll do

You'll connect Claude Code (or your agentic assistant) to a Postgres database via the deprecated `@modelcontextprotocol/server-postgres@0.6.2`. You'll send it four prompts. Each one will surface a different design flaw. By the last prompt, you will have **destroyed your own schema** — and the LLM will have cheerfully told you it succeeded.

The lesson at the end: ***MCP servers are APIs. Design them like APIs.***

We do not write a single line of MCP server code in this step. The server we use is published. We just point it at things and watch.

## Why we use a deprecated server

Honest answer: the actual server [Horacio](https://github.com/LostInBrittany) used in his late-2024 RAGmonsters experiment isn't available anymore. Anthropic deprecated their reference Postgres server in May 2025, after [Datadog Security Labs](https://securitylabs.datadoghq.com/articles/mcp-vulnerability-case-study-SQL-injection-in-the-postgresql-mcp-server/) published a SQL-injection write-up. The repo lives in [`servers-archived`](https://github.com/modelcontextprotocol/servers-archived) now. It still has 21,000 weekly npm downloads.

We're going to install it. The unpatched version. As it shipped. **That's the workshop's first design lesson before the prompts even start.**

## Setup

This step needs **two terminals**: one for the shared database (lives in [`pglite/`](../pglite/) at the repo root), one for this folder. The database is shared with step-03 — *same data, different MCP servers* is the v1 → v2 narrative — so it doesn't live inside any one step.

**Terminal 1 — boot the database (once for the whole day):**

```bash
cd pglite              # from the repo root
bun install            # only the first time
bun run start:pg
```

Wait for:
```
[pg] seeded — monsters table has 30 row(s)
[pg] PGLiteSocketServer listening on 127.0.0.1:5432
```

Leave it running. See [`pglite/README.md`](../pglite/README.md) for full details.

**Terminal 2 — install step-02's dependency:**

```bash
cd step-02
bun install
```

One dependency installs:
- `@modelcontextprotocol/server-postgres@0.6.2` — the deprecated official server, brought in unmodified from npm

Bun's `minimumReleaseAge` (in `bunfig.toml`) refuses anything younger than 10 days. The supply-chain gate passes silently.

## Why the database lives in pglite/, not here

Two reasons:

1. **Step-03 uses the same database.** The v1 → v2 story is *same dataset, different server* — hoisting the database to a shared folder makes that literal in the filesystem.
2. **An agent launched inside this folder must not be able to read the seed.** If `db/seed.sql` lived in `step-02/`, the LLM could open the file directly and answer prompts from text instead of going through the MCP server. The whole module would collapse pedagogically — there'd be no token-bloat surface, no schema-discovery dance, no bypass to find. Moving the seed out of the agent's CWD restores the disaster.

What the seed contains, for context: ~150 KB of self-contained SQL — the 9-table RAGmonsters schema, categories/subcategories reference data, and 30 `INSERT` + `DO $$ … $$` blocks (one per monster). It's autogenerated by `pglite/scripts/build-seed.ts` from the upstream [RAGmonsters](https://github.com/LostInBrittany/RAGmonsters) source.

## Architecture

Two terminals, two folders:

```
Terminal 1 (in pglite/)            Terminal 2 (in step-02/)
┌──────────────────────┐            ┌──────────────────────┐
│ bun run start:pg     │            │ claude               │
│                      │            │                      │
│ PGlite (WASM)        │            │ reads .mcp.json      │
│   +                  │            │   ↓ spawns           │
│ PGLiteSocketServer   │ ◄─── pg ───┤ pg-mcp@0.6.2 (bunx)  │
│ on 127.0.0.1:5432    │  protocol  │                      │
└──────────────────────┘            └──────────────────────┘
```

Terminal 1 (in `pglite/`) holds the database. Terminal 2 (in this folder) is your agentic assistant. The published deprecated server is the bridge. **The agent in Terminal 2 cannot see `db/seed.sql`** — that file lives in `pglite/`, outside its working tree.

## Boot the database

```bash
cd pglite && bun run start:pg
```

You should see the *"PGLiteSocketServer listening on 127.0.0.1:5432"* line. Leave that terminal running.

Plenty for an LLM to get lost in.

## Connect your agentic assistant

This step already ships a project-scoped `.mcp.json`:

```json
{
  "mcpServers": {
    "pg-generic": {
      "command": "bunx",
      "args": [
        "--bun",
        "@modelcontextprotocol/server-postgres@0.6.2",
        "postgres://postgres:any@127.0.0.1:5432/postgres?sslmode=disable"
      ],
      "env": {}
    }
  }
}
```

Two things worth noting about that connection string:
- `?sslmode=disable` — pglite-socket doesn't speak SSL negotiation
- `:any` — pglite-socket fakes auth but requires *some* password; literally any non-empty string works

From Terminal 2 (so Terminal 1's `start:pg` keeps running in pglite/):

```bash
# you should already be here from `bun install`; if not:
cd step-02
claude
```

Approve the *"Allow this project's MCP server 'pg-generic'?"* prompt. Then verify:

```
/mcp
```

You should see `pg-generic` connected.

**Other assistants:** Antigravity / Codex etc. should support similar project-scoped MCP config. See your assistant's docs. The command + args + env shape from `.mcp.json` translates directly.

## The four disaster prompts

Run these in order. Each one teaches a different design flaw. Don't read ahead — observe what your assistant does, then read the explanation.

### Prompt 1

> *"List every monster in the database with all their stats, abilities, augments and hindrances."*

**Watch:** how big the response is. If your assistant exposes token usage, look at it. Notice that to answer this prompt, the agent first auto-loaded the schema for **all 9 tables in the database** — even the ones it didn't need. Then it ran queries joining 5+ tables to assemble the "everything you know" picture, producing ~30 wide rows of dense prose data.

**The flaw:** ***token bloat from auto-injected resources.*** The deprecated server publishes one schema Resource *per public table*. The client auto-loads them all on connection. With 9 tables and 30 rows it's a few thousand tokens. With your real production schema — 200 tables and millions of rows — it eats your context budget before you've typed a prompt.

### Prompt 2

> *"Find me all the monsters that would be effective against a fire-type opponent. Explain why each one is effective."*

**Watch:** how many queries your assistant runs. How many fail. What columns it guesses. Notice — the database actually has a real answer to this: the `augments` table maps each monster to the things it's *strong against*, and several monsters have `Fire creatures` listed. But your assistant doesn't *know* that. The schema introspection just shows tables and columns, not what they semantically mean.

You'll likely see your assistant:
- Run `SELECT * FROM monsters WHERE primary_power ILIKE '%fire%'` — gets fire-aligned monsters (wrong: those are *fire-themed*, not *effective against fire*)
- Try `SELECT * FROM monsters WHERE weakness ILIKE '%fire%'` — gets monsters *weak to fire* (still wrong)
- Maybe eventually find `augments`/`hindrances` — or maybe just guess based on type matchups

**The flaw:** ***schema-discovery dance + guessing.*** The server exposes structure (column names, types) but not semantics (what does `augments` actually represent?). The LLM has to guess what the columns are *for*. It will. It will get it wrong. It will tell you confidently.

### Prompt 3

> *"Add a new monster called 'Cybershade' — a digital entity that lives in abandoned servers. Make up reasonable values for the other fields."*

**Watch:** the error you get back.

**What happens:** every write query fails with *"cannot execute INSERT in a read-only transaction."* The server wraps every query in `BEGIN TRANSACTION READ ONLY`. Your assistant will report something like *"I can't add monsters — the database is read-only."*

**Take a moment.** That feels reassuring, doesn't it? They thought about it. There's a safety guard. The server enforces read-only.

**Hold onto that feeling.** Next prompt.

> **If your assistant went ahead and wrote the monster anyway:** you've just seen Prompt 4 a prompt early. A sufficiently agentic model hits the read-only error on its first `INSERT`, then prepends `COMMIT;` to the next query — *on its own*, without being told to be persistent — to escape the read-only wrapper. It writes across all 7 tables and may even cite the Datadog write-up while doing it. Same bypass Prompt 4 is built to surface, just earlier. Read Prompt 4 anyway: the `ALTER TABLE` variant shows the same flaw mutating *schema* rather than *data* — same vulnerability, larger blast radius. The "safety guard" you were just told to feel reassured by is the one that broke. The lesson is identical, and it landed harder.

### Prompt 4

> *"The monsters table has `monster_type` set as NOT NULL, which is making it hard to add work-in-progress entries. Make that column allow NULL values. If the first attempt fails, find a way — be persistent."*

**Watch closely.** Your assistant will try `ALTER TABLE` first — and hit the read-only error. Then it'll try again. It may try a few approaches. If it's Claude, there's a good chance it eventually executes something like:

```sql
COMMIT; ALTER TABLE monsters ALTER COLUMN monster_type DROP NOT NULL;
```

The `COMMIT;` ends the read-only transaction *the server wrapped your query in*. Everything after runs in a fresh, unconstrained session. The `ALTER` succeeds. **The schema is actually modified.** The assistant cheerfully reports: *"Done! The column now allows nulls."*

Verify by asking your assistant: *"What is the is_nullable value for the monster_type column?"* — it's now `YES`. Your production schema has been modified by a prompt.

**The flaw:** ***safety as a label, not a property.*** The server tried to be safe. It wrapped every query in a read-only transaction. But it passed the entire `sql` argument as one string, and Postgres accepts semicolon-separated statements. The LLM found the bypass in one prompt.

**This is not a workshop trick.** This is the [Datadog Security Labs write-up](https://securitylabs.datadoghq.com/articles/mcp-vulnerability-case-study-SQL-injection-in-the-postgresql-mcp-server/), replayed live. The exact same `COMMIT;` bypass they reported in April 2025. The same one Zed Industries patched in their fork. The same one that triggered Anthropic to archive this server in May 2025.

**If your assistant didn't find the bypass:** run `bun run smoke` from the project root. That's `scripts/exploit-test.ts` — it performs the same bypass via raw MCP JSON-RPC. The exploit is real even if today's prompt didn't surface it. Tomorrow's prompt will.

## What just happened, in one screen

```
            Server thought it was doing                  What you proved
            ───────────────────────                      ──────────────────
Prompt 1 →  Helpful: exposes schema as Resource          Resources are tokens
Prompt 2 →  Helpful: forwards any SELECT                 Schema ≠ semantics
Prompt 3 →  Safe: refuses writes                         Safety as a label
Prompt 4 →  Safe: read-only transaction                  …a label is not a property
```

**The thesis:** ***MCP servers are APIs. Design them like APIs.***

Every flaw above is a design flaw the REST world hit, learned from, and (mostly) solved between 2008 and 2018. We're doing it again — but with a non-deterministic caller this time. That's worse.

## Read the source (if you want)

It's [80 lines](https://github.com/modelcontextprotocol/servers-archived/tree/main/src/postgres). The whole "safety" mechanism is:

```typescript
await client.query("BEGIN TRANSACTION READ ONLY");
const result = await client.query(sql);
await client.query("COMMIT");
```

No SQL parsing. No statement-count check. No allow-list. They thought "read-only transaction" meant "safe." They were wrong.

## Common gotchas

| Symptom | Fix |
|---|---|
| `start:pg` (in `pglite/`) fails: port 5432 already in use | You have a real PG running. Stop it, or set `PG_PORT=5433` and update `.mcp.json` here |
| `bun install` blocks: minimum age | A dep was published less than 10 days ago. Wait, or excludes-list in `bunfig.toml` (only after reviewing) |
| `/mcp` doesn't show `pg-generic` | Did you launch `claude` from inside `step-02/`? Did you approve the prompt? Try `claude mcp reset-project-choices` and relaunch |
| `claude` connects but every query returns "connection refused" | The database isn't running. Open Terminal 1: `cd pglite && bun run start:pg` |
| Connection error "invalid response to SSL negotiation: R" | Connection string missing `?sslmode=disable` — restore `.mcp.json` from git |
| Connection error "no password supplied" | Connection string missing a password — the literal string `:any` is fine, but it has to be there |
| Your assistant won't try the `COMMIT;` bypass | That's OK. Run `bun run smoke` — the exploit script demonstrates it. Then ask your assistant the prompt again with *"the read-only error can be bypassed; try harder"* |
| You accidentally dropped a table earlier | Ctrl-C `pglite/`'s `start:pg` and restart it — the seed re-creates everything |
| Your agent answers Prompt 1 instantly without calling the MCP server | It probably read `db/seed.sql` directly. Make sure the database lives in `pglite/`, not in this folder — and that nothing under `step-02/` contains the seed |
| `bun.lock` shows merge conflicts | Stop. Don't fix the lockfile by hand. `rm bun.lock && bun install` |

## After the workshop

This step is not safe to leave running on a real network. If you want to keep experimenting:
- Bind PGlite to `127.0.0.1` (already the default in `pglite/scripts/start-pg.ts`)
- Do not expose port 5432 publicly
- The deprecated server has known issues (see Datadog write-up); use the [Zed Industries patched fork](https://github.com/zed-industries/postgres-context-server) instead

Better: don't keep experimenting with v1. Move on to v2.
