# Phase 4.1 — Where this hurts (an observation pass)

> **Principle:** *Nothing here is broken. Everything here scales badly. That's what a gateway fixes.*
> **Time:** ~5 minutes
> **Files touched:** 0 (this is a structured look at what 4.0 left)

## Why

Before we build a gateway in 4.2, name what it solves. A solution looking for a problem is a tutorial. A solution that answers a felt problem is a lesson.

Spend 5 minutes touring what 4.0 produced and naming the four pains the gateway will absorb in 4.2. Then we go.

## The four observation beats

### Beat 1 — Count the tools

In Claude Code, run:

```
/mcp
```

Count what's exposed to the LLM:
- `catalog-server`: 4 tools (`search_monsters_by_category`, `get_monster_details`, `list_categories`, `compare_monsters`) + 2 resources + 1 prompt
- `arena-server`: 2 tools (`simulate_battle`, `record_battle_result` — though `record_battle_result` is still a TODO stub)

**Total surface: 6 tools, 2 resources, 1 prompt across 2 servers.** Multiply mentally: a real fleet might have 5–10 servers. The agent's context window grows linearly per turn.

### Beat 2 — Look at `.mcp.json`

```bash
cat .mcp.json
```

Notice:
- Two server entries, two `env` blocks
- `MCP_PRINCIPAL=developer` is **duplicated** in the catalog block (and would need to be added to arena if we wanted arena's future write Tools gated by the same principal)
- `DATABASE_URL` lives only in the catalog block — but if some other server needed it too, you'd duplicate it
- If you wanted to enforce principal-per-server (catalog=`developer`, arena=`guest`), each gets its own line

**That's not "auth across the fleet" — that's auth copy-pasted across the fleet.**

### Beat 3 — Find a fleet-wide answer to a fleet-wide question

Ask: *"What did the LLM call in the last 5 minutes?"*

Each `"Who wins between X and Y?"` prompt reliably writes **three lines** across **two files** (two `get_monster_details` in catalog's log, one `simulate_battle` in arena's). To reconstruct the trace you'd need to:
```bash
cat catalog-server/logs/server.log    # two lines per battle
cat arena-server/logs/arena.txt       # one line per battle
# … and merge by timestamp by hand
```

Two log files, two formats, no merge, no shared timestamp ordering, no per-principal filtering. **Across a fleet of 5 servers you'd have 5 logs to grep, 5 formats to normalise — and a single user prompt could span any subset of them.**

### Beat 4 — Name collisions

Quick thought experiment (don't actually do this if you don't want to revert):

If you renamed `arena-server`'s `simulate_battle` to `compare_monsters` — the same name catalog already uses — what does Claude Code show? **Two tools with the same name.** The MCP spec doesn't require global uniqueness across servers; clients vary in how they disambiguate. **In practice this is a foot-gun.**

## The four pains, named

| Pain | Symptom in 4.0 | What the gateway will give us (4.2) |
|---|---|---|
| Surface bloat | 6 tools × 2 servers in `/mcp` | One namespace, browsable: `catalog.*`, `arena.*` |
| Duplicated config | `MCP_PRINCIPAL` per server in `.mcp.json` | One env at the gateway, forwarded down |
| Fragmented audit | Per-server log files | One JSONL audit at `gateway/logs/audit.log` |
| Name collisions | Two tools called `compare_monsters` is undefined behaviour | `catalog.compare_monsters` vs `arena.compare_monsters` is unambiguous |

Plus a fifth pain we won't fix in this module but will name in 4C:

| Pain | Symptom | Future answer |
|---|---|---|
| No fleet-wide policy | Each server enforces its own rules | Policy lives in the gateway; servers stay focused |

## What this state delivers

A list of named problems. The next iteration solves them.

**Principle landed:** *Nothing in 4.0 is broken. Everything in 4.0 scales badly. The gateway is the place where the cross-cutting concerns move.*
