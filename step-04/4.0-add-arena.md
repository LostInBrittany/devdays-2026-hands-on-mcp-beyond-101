# Phase 4.0 — Add the arena (LLM orchestrates)

> **Principle:** *Composition happens at the agent layer by default. Servers are flat. The LLM is the conductor — it pulls lore from one server and hands it to another to get a verdict.*
> **Time:** ~10 minutes
> **Files touched:** 1 — `arena-server/src/tools/simulate-battle.ts`

## Why

You have a v2 catalog server (the `step-03/solutions/3.8/` build, mounted unchanged at `catalog-server/`). You're about to stand up a second MCP server next to it — `arena-server` — that resolves monster battles.

The arena does not know what monsters exist. It does not connect to the database. **It accepts two full monster detail payloads** — the `data` objects returned by catalog-server's `get_monster_details` — and derives combat stats from those payloads. The catalog owns lore (powers, weakness, behaviour); the arena owns combat math but the math is *rooted* in the lore. **Neither server knows about the other's data model.** That's the whole point of flat composition.

**The LLM is the conductor.** To answer *"who wins between Thunderclaw and Aquafrost?"* it must:
1. Call `get_monster_details({ name: "Thunderclaw" })` on catalog
2. Call `get_monster_details({ name: "Aquafrost" })` on catalog
3. Hand both `data` objects to `simulate_battle` on arena

No backend-for-frontend, no service mesh — just a smart caller that knows how to chain primitives. **The arena rejects shortcuts:** if the LLM tries to call `simulate_battle` with just names, the score derivation degenerates (and the description tells the LLM explicitly not to do that). The composition is *load-bearing* — without the catalog calls, there's no verdict.

A note on determinism: `deriveStats` is deterministic over its input, but the LLM may marshal the catalog payload slightly differently between runs (truncation, field reordering, paraphrasing of free-text). **So the same pair of monsters may produce different scores on different runs.** That's fine — the workshop wants composition, not reproducibility.

This phase ships the architecture. 4.1 makes you feel the friction. 4.2 introduces the gateway.

## Steps

1. Make sure `pglite/`'s `bun run start:pg` is alive on `127.0.0.1:5432`. The catalog-server needs it.
2. In `step-04/`, run `bun install`.
3. Open `arena-server/src/tools/simulate-battle.ts`. Read the file top-to-bottom — `deriveStats(details)` and the `monsterDetailsInput` Zod schema are provided; you fill the TODO inside the handler. The contract is:
   - **Input:** `monster_a`, `monster_b` — each a monster's full `data` payload (object with `name` required, plus any subset of catalog fields like `primary_power`, `weakness`, `behavior_ecology`, etc.).
   - **Output:** `{ winner, loser, reason, stats, source }` as a JSON string in a `content[0].text` envelope.
4. Implement the resolver:
   - Build `a` and `b` by spreading `deriveStats(payload)` onto each payload's `name`.
   - `score(m) = m.attack + m.defense + m.speed`
   - Higher score wins. Ties broken by alphabetically larger name (i.e. lex-smaller name loses).
   - `reason` is `"<winner> (score=N) beat <loser> (score=M)"`.
   - Echo both stat blocks back under `stats: { [a.name]: a, [b.name]: b }` so the LLM (and the audit log) can see what the arena rolled.
5. Save. (No `bun --hot` running yet — Claude Code spawns each server on its own.)
6. `cd step-04 && claude`. Approve **both** MCP prompts (catalog-server + arena-server).
7. Run `/mcp`. You should see both servers listed; total tools should include `simulate_battle` plus the four catalog tools.

## The change — fill in simulate-battle.ts

Replace the TODO stub body with:

```typescript
async ({ monster_a, monster_b }) => {
  const start = Date.now();
  logCall("simulate_battle", { a: monster_a.name, b: monster_b.name });

  const a = { name: monster_a.name as string, ...deriveStats(monster_a) };
  const b = { name: monster_b.name as string, ...deriveStats(monster_b) };

  const scoreA = a.attack + a.defense + a.speed;
  const scoreB = b.attack + b.defense + b.speed;

  let winner: typeof a;
  let loser:  typeof a;
  let winnerScore: number;
  let loserScore:  number;
  if (scoreA > scoreB) {
    winner = a; loser = b; winnerScore = scoreA; loserScore = scoreB;
  } else if (scoreB > scoreA) {
    winner = b; loser = a; winnerScore = scoreB; loserScore = scoreA;
  } else {
    // tie — alphabetically larger name wins ("first in line is on the losing end")
    if (a.name.localeCompare(b.name) > 0) {
      winner = a; loser = b;
    } else {
      winner = b; loser = a;
    }
    winnerScore = loserScore = scoreA;
  }

  logResult(
    "simulate_battle",
    `winner=${winner.name} (${winnerScore}) loser=${loser.name} (${loserScore})`,
    Date.now() - start,
  );

  return {
    content: [{
      type: "text",
      text: JSON.stringify({
        winner: winner.name,
        loser:  loser.name,
        reason: `${winner.name} (score=${winnerScore}) beat ${loser.name} (score=${loserScore})`,
        stats:  { [a.name]: { ...a }, [b.name]: { ...b } },
        source: "arena-server",
      }, null, 2),
    }],
  };
},
```

The `logCall` / `logResult` calls come from the `import { logCall, logResult } from "../log.ts";` line already at the top of the file. They emit one line per call to `arena-server/logs/arena.txt`.

**Two server logs, three calls visible, one stitched answer in Claude Code.** The LLM orchestrated: pull lore (×2), then resolve. The arena response includes a `stats` field so the audit shows exactly what the arena rolled for each fighter.

**Nobody told the LLM to compose. It composed because the tools were shaped for composition** — the arena's Tool description says "PREREQUISITE: call get_monster_details first", and the input schema names the catalog fields it expects.

If the LLM tries to call `simulate_battle` with bare names (skipping the catalog step), the input still validates (only `name` is required) but the score is derived from a near-empty payload — every monster collapses into the same tiny equivalence class and the verdict is meaningless. **That's diagnostic, not a bug:** description quality is what makes the difference between "the LLM uses it correctly" and "the LLM works around it". If you see that happen, point at the Tool description and ask: *what would you tighten?*

Try a follow-up that's clearly lore-shaped (*"What is Thunderclaw weak to?"*) — that one should produce catalog-only traffic; the arena stays silent. **Same surface, two different orchestrations.**
