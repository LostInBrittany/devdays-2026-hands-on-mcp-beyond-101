# Phase 4.2 — Build the gateway

> **Principle:** *Cross-cutting concerns belong in one place. Every server would otherwise reinvent its own auth, logging, audit, rate-limits. Move them out. The gateway is the place.*
> **Time:** ~20 minutes
> **Files touched:** 3 — `gateway/src/server.ts` (fill in stubs), `.mcp.json` (collapse two entries to one), plus a glance at `gateway/src/children.ts` (provided)

## Why

4.1 named four pains: surface bloat, duplicated config, fragmented audit, name collisions. All four are cross-cutting concerns — they're identical across every server in the fleet, and they grow worse with each server added.

The gateway is where they live exactly once.

A gateway is both:
- **An MCP server** to Claude Code (it speaks the protocol over stdio like any other)
- **An MCP client** to its children (it speaks the protocol to catalog-server and arena-server)

Both halves are wired in the skeleton. What you write is the **behaviour**: merge each child's manifest, prefix tool names with the child's name (using `.` as the namespace separator), route incoming calls to the right child, write one audit line per call.

A small SDK detail: `McpServer.registerTool` expects a Zod schema. Children publish JSON Schema. Re-deriving Zod from JSON Schema would drop descriptions and enum constraints — exactly the kind of contract erosion the rest of this module argues against. So the skeleton wires the low-level `server.server.setRequestHandler` for `tools/list` and `tools/call` and forwards each child's JSON Schema verbatim. Your `mergeManifests` only has to populate a `Map`.

### Step 2 — Implement `auditLine` (3 min)

Replace the stub at the top of `gateway/src/server.ts`:

```typescript
export function auditLine(entry: AuditEntry): void {
  const line = JSON.stringify(entry);
  console.error(line);
  try {
    appendFileSync(AUDIT_FILE, line + "\n");
  } catch {
    // logging must never break the server
  }
}
```

Why JSONL? Because in 4.3 and 4.4 we'll grep it; line-delimited JSON is `jq`-friendly.

### Step 3 — Implement `mergeManifests` (10 min)

Replace the TODO body with:

```typescript
async function mergeManifests(children: ChildClient[]): Promise<void> {
  for (const child of children) {
    const { tools } = await child.client.listTools();

    for (const tool of tools) {
      const namespacedName = `${child.name}.${tool.name}`;
      mergedTools.set(namespacedName, {
        child,
        originalName: tool.name,
        namespacedName,
        description: `[via ${child.name}] ${tool.description ?? ""}`.trim(),
        inputSchema: tool.inputSchema,
      });
    }

    console.error(`[gateway] merged ${tools.length} tools from ${child.name}`);
  }
}
```

What this does:
- For each child (catalog, arena), call `listTools()` over the MCP connection
- For each tool returned, store a **passthrough** entry in `mergedTools` keyed by `${child}.${tool}`, carrying the child's `inputSchema` verbatim
- The skeleton's `ListToolsRequestSchema` handler reads from this map and republishes each entry on the gateway; the `CallToolRequestSchema` handler looks up the namespaced name, strips the prefix in `originalName`, and dispatches through `routeToolCall`

**Why `.` and not `/`:** MCP tool names allow `[A-Za-z0-9_.-]` only — `/` triggers an SDK warning and may be rejected by stricter clients. `.` reads as a namespace separator and stays inside the spec.

**Resources and prompts:** the skeleton doesn't namespace them. That's a deliberate workshop trade — the audit story lands via tools (where 4.4's idempotency also lives). If you finish early, namespace resources too with a similar map + low-level `ListResources`/`ReadResource` handlers.

## Observe

Re-run the canonical battle prompt:

> **"Who wins between Thunderclaw and Aquafrost?"**

Watch the audit log. You should see **three lines** (one per child call), all with the same `principal=developer`, two from `catalog` and one from `arena`:

```jsonl
{"ts":"...","principal":"developer","child":"catalog","primitive":"tool","name":"get_monster_details","args_hash":"...","status":"ok","duration_ms":12}
{"ts":"...","principal":"developer","child":"catalog","primitive":"tool","name":"get_monster_details","args_hash":"...","status":"ok","duration_ms":9}
{"ts":"...","principal":"developer","child":"arena","primitive":"tool","name":"simulate_battle","args_hash":"...","status":"ok","duration_ms":1}
```

**Three calls, three lines, one principal, one file.** That's the gateway earning its keep — the same three lines that 4.1 made you grep across two per-server logs are now one `tail -f` away. (The order may vary if the LLM interleaves catalog fetches with the resolver call, but the count is fixed: arena's schema demands both payloads, so both catalog calls always fire.)

(`catalog-server/logs/server.log` still exists and still receives per-handler logs — that's the *application*-level trace inside catalog. The gateway audit is the *fleet*-level trace. Both are useful; they answer different questions.)

## What this state delivers

A single entry point that fans out to two backend servers, namespaces everything, and gives you one audit log to grep.
