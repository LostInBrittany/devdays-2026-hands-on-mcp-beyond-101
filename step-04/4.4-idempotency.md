# Phase 4.4 — Idempotency for the LLM era

> **Principle:** *In REST, retry safety was a polite concern. In MCP, it's a budget concern. Idempotency is a gateway concern, not a server concern.*
> **Time:** ~15 minutes
> **Files touched:** 2 — `arena-server/src/tools/record-battle-result.ts` (implement the write), `gateway/src/idempotency.ts` (fill in the dedupe table)

## Why

The LLM retries. A lot. Same intent, slightly different wording, sometimes within the same turn — and your DB has no idea those two calls were "the same." One write becomes two rows. Or twenty.

In REST, retry safety was a polite concern (the `Idempotency-Key` header is in RFC drafts, not RFC 7231). In MCP, it's a *budget* concern — the LLM's retry behaviour is part of the cost model. Your gateway needs to dedupe by intent so the underlying servers stay naïve.

The architectural decision lands here: **idempotency is a gateway concern, not a server concern.** The underlying Tool stays naïve — same handler whether it's the first call or the tenth. The gateway holds the dedupe table.

That's v3's thesis re-applied: cross-cutting concerns belong in the gateway.

## Files touched

```
arena-server/src/tools/record-battle-result.ts   ← implement the write (~10 lines)
gateway/src/idempotency.ts                       ← fill in check + record (~10 lines)
```

You will NOT touch `gateway/src/server.ts` — the idempotency hook in `routeToolCall` is already wired. It just needs the `idempotency.ts` functions to do something.

## Steps

### Step 1 — Implement the write Tool (2 min)

Open `arena-server/src/tools/record-battle-result.ts`. Replace the TODO stub body with:

```typescript
async ({ winner, loser, idempotency_key }) => {
  void idempotency_key;  // intentional: the gateway dedupes, this Tool doesn't

  if (!existsSync(DATA_DIR)) mkdirSync(DATA_DIR, { recursive: true });
  const record = { ts: new Date().toISOString(), winner, loser };
  appendFileSync(LOG_FILE, JSON.stringify(record) + "\n");

  return {
    content: [{
      type: "text",
      text: JSON.stringify({
        recorded: record,
        source: "arena-server",
      }, null, 2),
    }],
  };
},
```

Save. Restart the gateway (it re-discovers child manifests on init).

### Step 2 — Implement the dedupe table (5 min)

Open `gateway/src/idempotency.ts`. Replace the `check` and `record` TODOs:

```typescript
export function check(key: string): DedupeEntry | undefined {
  const entry = table.get(key);
  if (!entry) return undefined;
  if (Date.now() - entry.ts > TTL_MS) {
    table.delete(key);
    return undefined;
  }
  return entry;
}

export function record(key: string, result: unknown): void {
  table.set(key, { result, ts: Date.now() });
}
```

That's it. ~10 lines. The `routeToolCall` in `gateway/src/server.ts` already calls these helpers before forwarding any tool call whose args include `idempotency_key`.

### Step 3 — Wire `.mcp.json` (no change needed)

Already correct from 4.2 — `MCP_PRINCIPAL=developer` on the gateway. No new env vars for idempotency (the dedupe table is in-memory, in the gateway process).

### Step 4 — Verify the write path works (2 min)

Restart Claude Code. In a side terminal:

```bash
tail -f gateway/logs/audit.log
```

In another:

```bash
ls -la arena-server/data/ 2>/dev/null
# nothing yet
```

In Claude Code, prompt:

> **"Record that Thunderclaw beat Aquafrost. Use idempotency key 'battle-001'."**

(The explicit key isn't realistic — agents will typically generate them — but it makes the demo reproducible.)

Watch the audit log. You should see one line for `arena.record_battle_result` with `cache=miss`. Then:

```bash
cat arena-server/data/battle-log.jsonl
# one line, the recorded battle
```

### Step 5 — Make the LLM retry (4 min)

The simplest way: just re-prompt with the same intent.

> **"That call may have timed out. Record the same result with the same idempotency key."**

The LLM will issue a second `record_battle_result` call with the same `idempotency_key: "battle-001"`. The gateway hits its dedupe table, returns the cached response, and writes a second audit line with `cache=hit`.

**The Tool is never called twice.** Watch the JSONL file:

```bash
wc -l arena-server/data/battle-log.jsonl
# still 1
```

But the audit log shows two:

```bash
grep -c 'record_battle_result' gateway/logs/audit.log
# 2
```

**One row written. Two calls logged. Same idempotency key. Different `cache` field.**

If the LLM doesn't re-issue with the same key (it might generate a new key, defeating the demo), you can:
- Tell it explicitly: "use the exact same idempotency_key as the previous call"
- Or instructor-demo via `bun run scripts/smoke.ts --retry-test` (if you've shipped that)

### Step 6 — Stretch (10 min, optional) — rate limit + `Retry-After`

If the room is moving fast: add a synthetic rate-limit to the gateway. In `gateway/src/server.ts`, before the idempotency check in `routeToolCall`, add a per-principal counter (in-memory `Map<principal, calls>`); when a principal exceeds N calls in the last minute, throw `RateLimitExceeded { retry_after_seconds: 30 }`. Watch what the LLM does with the error.

This is what France slide 227 ("Hard Limits + Per-Caller Quotas") teaches.

## Verify

End state across three files:
- `wc -l arena-server/data/battle-log.jsonl` → **1** (the underlying write)
- `grep -c '"name":"record_battle_result"' gateway/logs/audit.log` → **2** (the gateway saw two calls)
- `grep -c 'tool=record_battle_result' arena-server/logs/arena.txt` → **1** (arena's handler fired only once)

The third number is the proof: arena's logger sits *inside* the handler, so it only emits when the handler actually runs. The gateway short-circuited the second call before it ever reached arena. **The Tool never knew there was a retry.**

## Observe

Two audit lines in the gateway, one line in arena's log, one row on disk:

```bash
grep 'record_battle_result' gateway/logs/audit.log | jq -c '{name, args_hash, cache}'
# {"name":"record_battle_result","args_hash":"abc123","cache":"miss"}
# {"name":"record_battle_result","args_hash":"abc123","cache":"hit"}

tail arena-server/logs/arena.txt
# [ts] tool=record_battle_result args={"winner":"Thunderclaw","loser":"Aquafrost","idempotency_key":"k1"}
# [ts] result=record_battle_result wrote winner=Thunderclaw loser=Aquafrost 2ms

wc -l arena-server/data/battle-log.jsonl
# 1
```

**Three perspectives, same event. The asymmetry between them IS the lesson.**

> *"The Tool didn't know it was being retried. The DB didn't know it was being retried. The gateway knew. That's the whole pattern."*

## What this state delivers

The fifth and final iteration of v3. You can now:
- Compose two MCP servers behind a typed gateway
- Audit every call across the fleet in one JSONL file
- See contract changes (rename, schema tighten) propagate immediately
- Dedupe LLM retries at the fleet edge, leaving underlying Tools naïve

**Principle landed:** *Idempotency keys are how the LLM-era client tells your fleet "these two requests are the same intent." The server doesn't have to be smart. The gateway has to be honest.*
